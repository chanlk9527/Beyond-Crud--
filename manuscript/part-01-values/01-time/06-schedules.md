# 每天九点与未来预约

[第 1 章：时间不是一个 datetime](../01-time.md)

日报为指定日期生成一个区间；每天九点的日程则要不断生成下一次执行瞬间。未来预约还需要处理当地时刻不存在或重复的情况。

<a id="sec-1-6"></a>

## 1.6 每天九点，下一次是哪一刻

“九点”是一个当地时刻，“每个工作日九点”是一条重复规则。后者需要知道工作日、门店时区，再为每个日期生成一次执行时间。

像 `2027-04-01T09:00` 这样的当地日期时间，Java 用 `LocalDateTime` 表示。`Local` 表示值本身不带时区或偏移量，并不表示已经绑定当前电脑所在地。[Java 本地日期时间类型](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/LocalDateTime.html)

偏移量与地区时区也需要分开。`-05:00` 是固定数值，`America/New_York` 是一组随日期变化的规则。冬夏可能采用不同偏移量，政策也可能改变。IANA 时区数据库保存这些历史与规则；保存今天的偏移量不能代替保存地区时区。[IANA 时区数据库说明](https://data.iana.org/time-zones/tz-link.html)

<a id="sec-1-6-1"></a>

### 1.6.1 未来日程要保留什么

一场线上会议已经确认在 `2027-07-10T13:00:00Z` 开始。参与者分布在不同地区，页面各自显示当地时间，所有人参加的仍是同一场会议。有人出差后，日历上的显示会变，会议的开始时间点保持不变。这样的日程可以把已确认的时间点作为执行依据，改动它就意味着会议改期。

门店“每天上午九点开门”则需要另一种数据。今天的九点可以换算成一个 UTC 时间点，但这个结果只定位了今天的一次开门，无法完整表达以后的营业安排。系统还需要保存上午九点、门店所在的地区时区，以及每天执行的规则；如果只在工作日营业，还要知道哪些日期算工作日。

区别在计算下一次时间的方式。对于实行夏令时的地区，当地九点对应的 UTC 时刻在一年中可能变化。如果拿今天的执行时间不断加 24 小时，跨过时钟调整后，就可能在当地八点或十点开门。要保持每天当地九点，应先确定下一次营业日期，再结合九点和门店时区计算那一次的时间点。生成计划与实际执行如何配合，见[日报与计划执行](../../../examples/ch01-time/deep-dive.md#business-day-jobs)。

如果把生成的开门时间也存下来，它应随营业计划修改而更新。例如营业时间从九点改成十点，尚未执行的旧计划仍写九点，就会与新规则冲突。

未来的一次预约也可能要求保持当地时刻，例如明确约定某地某日上午九点到店。这时应保留当地日期时间与地区时区：如果当地在赴约前修改了时间规定，可能需要重算执行时间，并同步提醒。时区政策确实可能变化，但这属于需要按业务承诺处理的边界情况。[IANA 时区数据库更新示例](https://www.iana.org/time-zones/releases/2022e)

保存了当地日期、时刻和时区，接下来就要把它们换算成时间点。通常这一步很直接，但在时钟调整的日期，有些当地时刻可能不存在，也可能出现两次。

<a id="sec-1-6-2"></a>

### 1.6.2 重复的凌晨一点半，选择哪一次

回到纽约那两次时钟调整：春季的 `02:30` 不存在，秋季的 `01:30` 出现两次。当地日期时间加上地区时区，正常时有一个候选瞬间，落入缺口时没有，落入重叠时有两个。

一些库会替我们作选择。例如 Java 的 `ZonedDateTime` 常用构造方法会将落在缺口内的时间向后移动；对重叠时间也有默认的偏移量选择。默认行为让程序容易继续运行，但预约被移到另一个时间，并不一定符合业务约定。[Java `ZonedDateTime` 文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/ZonedDateTime.html)

因此预约输入需要明确的消歧策略：可以拒绝不存在的时间，请用户重新选择；对重叠时间，可以要求选择第一次还是第二次。日历任务则还需确定跳过、顺延或只执行一次的规则，不能默默沿用库的默认决定。

现在为预约选定一种明确策略：缺口拒绝，重叠让用户选择。实现时先查询候选偏移量，再决定能否形成唯一时间点。下面的流程图给出判断顺序。

![当地日期时间与地区时区可能得到零个、一个或两个偏移量，只有校验通过的候选才能形成唯一时间点](../../assets/ch01/05-local-time-resolution.svg)

图 1-7：这套预约策略有三条路径。缺口拒绝，唯一候选直接采用，重叠要求选择；若提交了偏移量，两条可继续的路径都必须校验它确实属于候选集合。

完整 Java 实现见[预约解析实验](../../../examples/ch01-time/deep-dive.md#local-time-resolution)。

Java 用 `ZoneId` 表示地区时区，用 `ZoneOffset` 表示一次解析采用的偏移量。用户不必记住 `-04:00` 和 `-05:00`：界面可以展示“第一次凌晨一点半”和“第二次凌晨一点半”，服务端返回对应候选值。若业务固定选择第一次，也应将这个策略写明并测试。

同时提交时区和偏移量时，还要验证它们是否相容。纽约的一个夏季时间配上冬季偏移量，在数学上可以解析成一个瞬间，却未必属于该地区那一天的真实规则。直接信任偏移量，会让“当地九点”的承诺失去意义；直接忽略偏移量，又可能把用户明确选择的第二次一点半改成第一次。

预约发生改期时，这个解析过程需要再执行。不能只改本地日期、沿用上一次的偏移量。日期变了，适用的规则也可能变。被保存的偏移量用于解释某一次解析结果，不应充当这个地区永久的属性。

若接口只接收带偏移量的时间点，没有地区时区，那么它承诺的就只是一个瞬间。这种接口适合许多场景，也更简单；只是不能再声称自己保留了当地日程。减少字段是合理取舍，前提是同时减少对应的承诺。

<a id="sec-1-6-3"></a>

### 1.6.3 让接口保留用户的选择

现在把这套选择接到预约接口上。输入保留当地日期时间、地区时区，以及必要时由用户选择的偏移量：

```json
{
  "local_start": "2027-07-10T09:00:00",
  "time_zone": "America/New_York",
  "selected_offset": null
}
```

这个接口固定采用 [1.6.2 节](#sec-1-6-2)的策略：缺口拒绝，重叠要求选择。普通时刻可省略 `selected_offset` 或传 `null`；遇到重复时刻，服务端返回候选偏移量，客户端让用户选择后重新提交。例如纽约 2025 年 11 月 2 日的 `01:30`，选择第二次就提交 `"selected_offset": "-05:00"`，服务端仍要校验它属于该日期的候选集合。这样，协议才真正接得上前面的解析策略。创建成功后返回带 `Z` 的 `starts_at`，并保留原始选择供编辑。

生成执行瞬间之后，还要决定任务迟到时补跑还是跳过。执行器应收到明确的计划输入，而不是启动时重新猜今天该做什么；具体调度模式、计划身份和补跑策略在[深入材料](../../../examples/ch01-time/deep-dive.md#business-day-jobs)中展开。
