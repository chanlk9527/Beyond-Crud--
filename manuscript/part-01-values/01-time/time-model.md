# 时间的语义模型

[第 1 章：时间不是一个 datetime](../01-time.md)

会员的日期、截止瞬间和有效区间并非同一个对象的三种格式。日期表达购买承诺，瞬间定位边界，区间规定哪些检查时刻满足条件。分清它们各自表示什么，才能解释为什么改一段字符串有时只是换显示，有时却改变了用户的权益。

## 1.3 时间值、时间量与时间规则

### 1.3.1 先区分对象，再选择类型

时间点回答“时间轴上的哪一刻”。两个采用共同时间尺度的时间点可以比较先后，也可以计算差值。同一个时间点，在上海和纽约会显示为不同的日期与时刻。同一瞬间的当地表示不同，不意味着事件发生了两次。

日期回答“日历上的哪一天”，当地时刻回答“钟表上几点”，当地日期时间将两者组合起来。`2027-07-10T09:00` 比 `09:00` 多了日期，却仍没有指出采用哪个时区。对跨地区的事件，不能仅凭两个当地日期时间的字面大小推断发生顺序：东京九点与纽约八点使用的参照不同。

持续时间和日历量则表达要增加或减少的量。三小时可以用于计算从某个起点经过多久；一个月要根据起始日期和日历规则确定结果。二者都不是事件发生时间，也不能独立充当截止。

表 1-2：本章的基本对象与 Java 类型对照。日期采用公历；类型名用于帮助辨认职责。

| 对象 | 它包含的信息 | 示例与类型 |
| --- | --- | --- |
| 时间点 | 时间轴上的位置 | 支付完成瞬间，`Instant` |
| 日期 | 年、月、日 | `2027-03-31`，`LocalDate` |
| 当地时刻 | 时、分、秒及小数部分 | `09:00`，`LocalTime` |
| 当地日期时间 | 日期与当地时刻，不含时区或偏移量 | `2027-07-10T09:00`，`LocalDateTime` |
| 持续时间 | 以秒及其小数单位计量的长度 | 连续三小时，`Duration` |
| 日历量 | 年、月、日组成的量 | 一个月，`Period` |

这些类型在 [Java 时间 API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/package-summary.html) 中具有不同职责。`Local` 表示不带时区或偏移量，并非“采用本机时区”。使用不同类型，可以更容易看出一个值保存了哪些信息、适合做哪些运算。

选择类型的依据是业务需要保存的事实。生日保存日期，营业时间保存当地时刻，已发生支付保存时间点，都可以是完整模型。只有当业务需要从日历值定位一个瞬间时，才必须补充转换条件。给所有日期强行配上午夜，并没有让数据更完整，反而引入了需要维护的新约定。

### 1.3.2 时区连接当地表示与时间轴

偏移量表示当地读数与 UTC 读数的差。已知完整的当地日期时间和偏移量，就可以定位一个瞬间；例如上海本例中的 `2027-04-01T00:00:00+08:00`，减去八小时后得到 `2027-03-31T16:00:00Z`。计算跨越日期边界，由日期时间库处理进位和退位。

地区时区提供的则是随时间变化的规则。`America/New_York` 不能简化为一个永远不变的 `-05:00`，因为不同日期可能采用不同偏移量。IANA 时区数据库维护地区的历史及规则，政策调整也会使这些规则更新。[IANA 时区数据库说明](https://data.iana.org/time-zones/tz-link.html)

给定一个时间点和确定版本的地区规则，可以查到该瞬间采用的偏移量，再得到当地表示。这是从时间轴向当地读数的转换。反过来，从当地读数寻找时间点，就需要查找哪些瞬间在该地区显示为这个读数。正常时找到一个；时钟向前跳过某段读数时可能找不到；向后重复时可能找到多个候选。

因此两个转换方向并不对称。将瞬间显示为当地时间是一项表示操作，将当地输入解析为瞬间则可能需要业务选择。预约的缺口与重叠正是这个映射关系的结果，后文会给出具体日期和处理流程。

带偏移量的日期时间已经可以定位瞬间，但单个偏移量不能恢复地区未来的规则。Java 的 `OffsetDateTime` 保存前一种信息，`ZonedDateTime` 还关联时区并包含已解析的偏移量。是否需要地区规则，取决于后续是否要继续按当地日历运算，而非类型越复杂越可靠。[Java 日期时间类型说明](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/package-summary.html)

### 1.3.3 运算关系决定算法

持续时间运算沿时间轴进行。起点为 `t`、长度为 `d` 时，终点是 `t + d`；在可表示范围内，将终点减去起点便得到同样的长度。“连续 168 小时有效”属于这个模型，换一种展示时区不改变计算结果。

日历运算操作的是日期字段。日期加一个月，先确定目标月份，再处理目标月是否存在原日号；当地日期时间加一天，先改变日期，再依据目标日期的地区规则定位瞬间。因此，日历运算一般不能预先折算为一个固定秒数，也不能假定连续两次加月总与一次加两月相同。下一节会从月末截断推导这种差别。

转换还可能丢失信息。一个时间点转换为某地区的日期，会丢掉这一天里的具体时刻；当地日期时间解析为时间点后，若不保留地区和原始选择，也无法仅凭瞬间恢复完整输入。“转回去”必须说明要恢复什么：恢复同一瞬间、同一日期还是原始编辑意图，是不同的要求。

同样，比较前必须确定相等的含义。`2027-04-01T00:00:00+08:00` 与 `2027-03-31T16:00:00Z` 文本不同，解析后的时间点相等。如果只比较字符串，就会误以为截止发生了变化。后面验证存取结果时，也要先确定该比较日期、瞬间，还是原始输入。

### 1.3.4 从基本对象构成业务规则

区间由边界和包含约定组成，重复日程由日期选择规则、当地时刻、地区时区和解析策略组成。它们建立在基本对象之上，却包含更多约束。一个 `LocalTime` 只能表达九点，无法表达“每个工作日九点”；一个 `expires_at` 只能定位截止，无法决定到期前获准的下载是否允许继续。

时间数据在业务中还具有不同角色。原始输入记录用户选择，规则负责生成结果，已确认的计划规定应当发生什么，事件记录保存实际发生了什么。例如，课程计划结束于十点，实际结束于十点半，不能通过更新同一个含糊的 `end_time` 把两者混在一起。否则录播有效期无论采用哪个值，都难以解释依据。

派生值是否需要持久化，要看它的用途。可以随时廉价计算的报名截止可以只在接口中返回；需要交给调度器的提醒时刻可能需要存储。存下来之后仍要保留依赖关系，使源数据变化时能够识别需要更新的结果。存储一个计算结果，不会自动把它变成独立的业务事实。

因此，设计一个时间字段时，要先说明它保存的是用户输入、计算结果，还是已经发生的事件，再选择类型。一个值看起来像时间戳，并不足以告诉我们应该怎样使用它。

### 1.3.5 本章时间模型的边界

本章面向普通业务系统，日期示例采用公历。工作日需要另外定义节假日和调休日历，其他历法也需要相应规则，不能从一个时区标识中推导出来。

时间轴上的数值运算还依赖采用的时间尺度。UTC、Unix 时间和具体语言库对闰秒的表达与处理不能直接视为同一件事；Java `Instant` 明确采用 Java Time-Scale。本文的小时、天长示例按所用库的模型计算，不声称普通系统时钟已经提供精密的物理时间测量。需要跨闰秒精确计量时，应核对时间源与库的尺度约定。[Java 时间尺度说明](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/Instant.html)
