# 业务日与时间区间

[第 1 章：时间不是一个 `datetime`](../01-time.md)

按日期汇总数据，是日历到时间轴转换的一个应用。它并不需要另一套时间算法：为一个业务日期求出相邻日界，再用半开区间选取事件即可。真正需要额外定义的是业务日采用什么边界，以及记录按哪一种事件归属。

<a id="sec-1-5-3"></a>

## 1.5 业务日与时间区间

### 1.5.1 先确定日期，再生成区间

“统计昨天的订单金额”中的昨天，必须相对于一个明确的业务日期计算。服务运行在 UTC 容器中，运营按北京时间看日报，不能直接使用服务器默认日期。可以先将本次统计采用的参考瞬间转换为业务时区中的日期，再减一个日历日；补跑历史报表时，则直接传入目标日期，避免每次运行重新解释“昨天”。

设 `B(D,Z)` 表示按约定求出的日期 `D` 在时区 `Z` 中的开始边界。一个自然日的查询范围为：

```text
start = B(D, Z)
end   = B(D + 1 个日历日, Z)
范围  = [start, end)
```

**这两个边界分别由日期解析而来**。不能先求 `start`，再假定 `end = start + 86400 秒`；前一节已经证明，在时区偏移改变的日期，这会改变覆盖范围。

以 `Asia/Shanghai` 的 2027 年 3 月 31 日为例：

```text
start = 2027-03-31T00:00:00+08:00 = 2027-03-30T16:00:00Z
end   = 2027-04-01T00:00:00+08:00 = 2027-03-31T16:00:00Z
```

![上海三月三十一日的两个日界分别换算为 UTC 三月三十日十六点和三月三十一日十六点](../../assets/ch01/08-business-day-range.svg)

图 1-3：当地日期的两个边界定位同一段 UTC 区间。日期文字变化不改变范围，横向不按比例。

若 `paid_at` 表示支付事件的时间点，参数也按时间点绑定，查询即可直接使用这个范围：

```sql
SELECT SUM(amount)
FROM orders
WHERE paid_at >= :start
  AND paid_at <  :end;
```

下一天从同一个 `end` 开始，交界瞬间只被下一天选中。包含两端的 `BETWEEN` 会使相邻日的查询在边界上重叠；使用一串 9 则重新引入存储精度依赖。这样，每条落在交界处的记录只会计入一天。

### 1.5.2 日界本身也是一项规则

通常一个自然日从当地零点开始，但时钟调整也可能发生在午夜。Java 的 `LocalDate.atStartOfDay(zone)` 根据地区规则求最早有效开始；缺口、重叠甚至整日被跳过的历史情况，需要按库行为与业务约定解释。不能先构造一个无条件存在的零点，再认为转换必然成功。[Java 日界计算](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/LocalDate.html#atStartOfDay(java.time.ZoneId))；具体案例见[日界实验](../../../examples/ch01-time/deep-dive.md#day-boundaries)。

业务日还可以采用其他界限，例如酒店夜审日或门店每天凌晨四点结算。此时应定义相邻日期各自的结算边界，并规定遇到当地时刻缺口或重叠时的选择。区间结构仍然适用，**变化的是边界生成规则**。自然日只是业务日的一种常用定义。

每日限额使用同一种分组机制。按账户固定时区重置时，用户旅行不改变归属；若按当前所在地重置，跨时区可能将用户放入另一个日期并重新获得额度。对于固定账户日的承诺，时区应来自受控的账户规则，而不能由每次请求任意提交。

### 1.5.3 时间范围与事件口径共同决定结果

固定区间只回答“哪些瞬间属于这一日”，还不能决定订单应该使用哪个字段。按支付日统计应选支付事件，按创建日统计应选创建事件。修改备注时更新的 `updated_at` 无法替代这两种事件，否则一条业务记录会随无关修改改变统计归属。

即使区间和事件字段完全相同，两次查询也可能得到不同结果。支付实际发生在昨天，回调今天才到达；昨天的事件范围没有变化，数据库可见的记录却增加了。因此应把**事件归属和数据可见性**分开：事件发生在哪一天，由统计口径决定；查询时能看到多少记录，则还受接收、补录和修正的影响。

要求重现某次已发布日报时，除保存日期口径外，还要明确当时采用的数据截面或版本。如何处理晚到、重算与补跑，集中见[日报与计划执行](../../../examples/ch01-time/deep-dive.md#business-day-jobs)。它们建立在已经确定的日期区间之上，不能靠给上限多加几小时解决。

这也解释了为什么“日期范围没变”并不保证“报表结果不变”。核对日报时，既要检查两端的时间边界，也要检查统计的事件和当时可见的数据。日期范围确定后，同一套计算还可以用于生成每天的营业安排。
