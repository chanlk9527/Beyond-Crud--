# “昨天”的数据到底有哪些

[第 1 章：时间不是一个 datetime](../01-time.md)

日历规则不仅生成会员截止，也决定一张日报包含哪些数据。前面只求一个截止边界，这次要为“昨天”找出完整区间，并明确统计的事件。

<a id="sec-1-5-3"></a>

## 1.5.3 把一天变成查询区间

现在来看一个很常见的需求：“统计昨天的订单金额。”

服务运行在 UTC 环境，运营团队按北京时间看日报，海外用户又有自己的自然日。需求只有一句“昨天”，代码却必须选一个。默认使用服务器日期，意味着搬一次部署环境就可能改变统计口径，这很难算作可靠的业务规则。

假设报表按 `Asia/Shanghai` 的自然日统计，目标日期是 2027 年 3 月 31 日。应当先在业务时区中找到这一天的开始和下一天的开始，再分别转换成数据库里使用的时间点：

```text
业务日期：2027-03-31
业务时区：Asia/Shanghai

start = 2027-03-31T00:00:00+08:00
      = 2027-03-30T16:00:00Z
end   = 2027-04-01T00:00:00+08:00
      = 2027-03-31T16:00:00Z
```

![上海三月三十一日的两个日界分别换算为 UTC 三月三十日十六点和三月三十一日十六点](../../assets/ch01/08-business-day-range.svg)

图 1-6：上海的一个业务日对应一段 UTC 区间，上下两行标出同两个瞬间。日期均在 2027 年，横向不按比例。

数据库查询使用两个已经确定的边界。下面的参数都表示时间点，具体绑定方式由数据库驱动决定：

```sql
SELECT SUM(amount)
FROM orders
WHERE paid_at >= :start
  AND paid_at <  :end;
```

这里再次采用半开区间，下一天的零点只属于下一天。不要用包含两个端点的 `BETWEEN` 来表达相邻自然日，也不要把上限补成一串 9。

对于实行夏令时的业务时区，`end` 应根据下一天的日期单独求出，而不是从 `start` 加 86,400 秒。否则那张日报不是少统计一小时，就是多统计一小时。处理一天时，日历决定边界，秒数只是两个边界之间的结果。

求日界时应使用地区规则。午夜也可能落入时钟调整的缺口，日期的开始未必是当地 `00:00`；Java 的 `LocalDate.atStartOfDay(zone)` 就会按规则选择该日期最早的有效时刻。具体处理见[日界实验](../../../examples/ch01-time/deep-dive.md#day-boundaries)。

同一个逻辑也适用于“用户每日限额”。需要明确限额按平台日、账户固定时区，还是按用户当前所在地重置。若使用当前位置，一个人跨越时区就可能重新获得一次额度，这未必是想要的规则。通常应该固定某个账户或业务时区，而不是让客户端随请求提交一个能改变额度的时区。

上面的查询按支付事件归属。如果运营要的是创建日的订单，应改用创建事件。即便区间固定，晚到回调也可能让重算结果变化；统计范围相同，不代表每次看见的输入相同。需要固定报表口径、重现旧结果或补跑时，再看 [日报与计划执行](../../../examples/ch01-time/deep-dive.md#business-day-jobs)。

会员有效期和日报都可以按日历生成区间。每天九点的营业安排还多一个要求：不断生成下一次，而不是只保存今天的结果。
