# 同一个瞬间，怎样穿过系统

[第 1 章：时间不是一个 datetime](../01-time.md)

截止边界已经确定。接下来让它经过用户展示、接口和数据库，检查每次转换是否仍然保留同一个瞬间。

<a id="sec-1-3"></a>

## 1.3 用户去了纽约，服务器也搬家了

<a id="sec-1-3-1"></a>

### 1.3.1 显示变了，有效期没有变

用户到纽约出差，打开同一个会员页面。界面可以显示他当地的截止时刻，但不能重新按纽约的 3 月 31 日生成一份有效期。购买时已经约定了上海日期，旅行改变的是观察位置。

同样，服务从北京机器迁到使用 UTC 的容器，授权结果也应保持不变。如果迁移让会员提前或推迟失效，说明某一层把机器配置当成了业务规则。

一个常见入口是 `formatTime()`。它没有时区参数，内部直接使用操作系统默认时区。迁移之后，页面显示变了；CSV 导出又走另一套格式化代码，于是同一笔业务出现两个日期，数据库里的值却可能完全正确。

把调用写成 `formatInstant(instant, displayZone)`，需要作出的选择就显露出来了。展示时区可以来自用户设置，也可以由产品固定，但应当说得出来源。日期格式则是另一个选择：中文界面可以显示纽约当地时间，英文界面也可以显示北京时间。语言和国家都不能直接替代明确的时区。

如果文案仍写“3 月 31 日当天有效”，就应说明它依据上海日期；如果改为展示精确截止时刻，则从同一个 `expires_at` 转换。用户不该通过文案猜测系统采用了哪一种规则。

检查一下：用户去纽约，服务器迁到 UTC，是否需要更新 `expires_at`？这两件事都不需要。前者可能改变显示，后者连业务显示都不应改变；只有业务有效期被修改，截止值才需要变化。

<a id="sec-1-3-2"></a>

### 1.3.2 接口不能让接收者猜

本例的接口可以返回：

```json
{
  "expires_at": "2027-03-31T16:00:00Z"
}
```

这个字段的约定是“开始失效的时间点”。接收方解析后用于比较，展示时再指定时区。若返回 `2027-04-01 00:00:00`，却不声明如何解释，上海环境可能把它读成上海零点，UTC 环境则可能读成 UTC 零点。两次解析都成功，得到的截止却相差八小时。

直接给当地时间追加 `Z` 也不会完成转换。把上海零点写成 `2027-04-01T00:00:00Z`，等于宣称截止在 UTC 零点，会员就被延长了八小时。应先根据原来的时区定位瞬间，再生成目标表示。

接口也可以传数字时间戳。常见 Unix 时间戳从 `1970-01-01T00:00:00Z` 起计数，但秒和毫秒并不是同一种单位。若使用数字，应当在协议中明确起点和单位，例如用 `expires_at_epoch_ms` 表示 epoch 毫秒。这里先选择带 `Z` 的字符串，让接收者不用再猜单位。

格式确定之后，还要约定允许的精度、范围和缺失含义。不能把零值同时解释成未知、永久有效和已经到期。更高精度的数字是否能穿过不同语言、严格解析如何设置，都可以在 [存取实验](../../../examples/ch01-time/deep-dive.md#storage-roundtrip) 中继续检查。

<a id="sec-1-3-3"></a>

### 1.3.3 沿着同一个截止值走一圈

现在把 `2027-03-31T16:00:00Z` 写入 PostgreSQL 的 `timestamptz` 列。这个类型按 UTC 保存瞬间，查询显示使用会话时区；它不保留最初的地区时区名称。[PostgreSQL 日期时间类型](https://www.postgresql.org/docs/current/datatype-datetime.html)

会话就是这次数据库连接采用的一组设置。把同一条记录先按上海时区查询，再按 UTC 查询，预期分别显示 `2027-04-01 00:00:00+08` 和 `2027-03-31 16:00:00+00`。文本变化符合设置，瞬间没有变化。

下面把数据库观察继续接回应用。表中结果是本例采用明确时间点绑定、读取映射和 UTC 序列化后的预期，不是所有驱动的默认行为。

表 1-2：同一个会员截止值经过应用、数据库和接口的往返。

| 所在位置 | 值或观察结果 | 要验证什么 |
| --- | --- | --- |
| 应用准备写入 | `2027-03-31T16:00:00Z` | 参数表示时间点 |
| 数据库列 | `timestamptz` 保存该瞬间 | 写入没有重新解释为其他地区的当地时间 |
| 上海会话查询 | `2027-04-01 00:00:00+08` | 只改变显示 |
| UTC 会话查询 | `2027-03-31 16:00:00+00` | 仍是同一瞬间 |
| 驱动读回应用 | 与原时间点相等 | 类型映射和约定精度正确 |
| 接口再次输出 | `2027-03-31T16:00:00Z` | 解析后仍与原时间点相等 |

完整 SQL 实验及另一种无时区列的对照放在 [存取实验](../../../examples/ch01-time/deep-dive.md#storage-roundtrip)。先看这组预期：如果客户端只是换成 `+08:00`，没有必要给数据库加减八小时；如果应用读回的瞬间已变，就应沿写入、列类型和驱动映射定位改变发生在哪一步。

最后再让读回的值参与边界判断。恰好在 `2027-03-31T16:00:00Z` 检查，仍应拒绝。一个值在数据库客户端里“看着正确”，还不足以证明应用使用它时也正确。

假设接口重新输出 `2027-04-01T00:00:00+08:00`，往返算不算失败？不算，两种表示定位同一瞬间。如果输出的是 `2027-04-01T00:00:00Z`，就已经改变了截止。验收时应比较解析后的时间点，而不只比较字符串。

![应用对象经参数绑定写入数据库，再经驱动读取、序列化和重新解析与原对象比较](../../assets/ch01/06-storage-roundtrip.svg)

图 1-2：验证要走过实际使用的转换链。沿箭头从写入走到重新解析，比较时间点及约定精度，而非只比较显示文本。

连接池可能给下一次请求换一个物理连接，会话设置必须在每个连接上成立；高精度值也可能在某一层损失。这两项都要通过实际驱动验证，不能只由数据库查询的显示推断。日期字段则应原样保持日期，不应该套用时间点的转换规则。

旧数据如果已经差了八小时，应先核对独立流水和写入来源，再决定修哪一层。[历史数据排查](../../../examples/ch01-time/deep-dive.md#historical-time-repair) 给出了具体路径。来源信息丢失时，转换函数不能自行恢复原意。

到这里，会员的截止值已经有了从规则到存取的检查办法。下一步把它放到真正决定能否访问的位置。
