# 时间的语义模型

[第 1 章：时间不是一个 `datetime`](../01-time.md)

会员的最后有效日期、截止瞬间和有效区间，已经让我们遇到了三种不同的时间对象。现在先放下会员规则，看看这些对象从哪里来、彼此怎样联系。理解这些关系之后，“七天有效”和“每月续费”就可以从各自的含义出发推导，而不必先猜应该调用哪个函数。

## 1.3 时间值、时间量与时间规则

本节面向普通业务系统，日历示例采用公历。先从时间轴上的位置与长度开始，再讨论人们使用的日期和时刻，最后用时区把两者连接起来。

<a id="_1-3-1-先区分对象-再选择类型"></a>

### 1.3.1 时间轴上的位置与长度

一笔支付完成时，上海用户的钟表显示下午三点，东京用户的钟表显示下午四点。他们看到的读数不同，支付却只完成了一次。先不考虑各地钟表怎样显示，把支付完成的位置标在同一条时间轴上，这个位置就是一个时间点，也称瞬间（instant）。

瞬间回答“何时发生”。把用户从上海换到东京，不会移动支付在时间轴上的位置。我们可以比较两个瞬间的先后，却不能只凭一个瞬间回答“当天是几号”：日期还要看采用哪里的日历表示。

要把时间轴上的位置保存成数字，需要先约定从哪里开始数。这个人为选定的计数起点称为纪元（epoch）。例如，以 `1970-01-01T00:00:00Z` 为起点、以秒为单位计数，零表示起点，一表示它之后一秒，负一表示它之前一秒。换用毫秒，同一个“之后一秒”就写成 1000。因此，数字时间戳离不开起点、单位和时间尺度的约定。

纪元让位置可以用数字表达，并不改变事件本身。Java 的 `Instant` 封装了这种位置，使用 epoch 秒及秒内纳秒部分表示；应用通常可以直接使用对象，而只在协议要求数字时处理单位转换。[Java `Instant` 的表示](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/Instant.html)

如果再标出支付开始的位置，就可以计算两点相隔多远。这个长度称为持续时间（duration）。在同一时间尺度内，设开始为 `a`，完成为 `b`，差值为三秒，则有：

```text
b - a = 三秒
a + 三秒 = b
b - 三秒 = a
```

这里加减的对象不同：两个瞬间相减得到长度，瞬间加上长度得到另一个瞬间；两个长度也可以相加，但把两个瞬间相加并没有对应的业务含义。**瞬间是位置，持续时间是长度**。Java 分别用 `Instant` 和 `Duration` 表达它们。持续时间也可以为负，例如用“开始减完成”表达方向相反的差值。

“三小时”可以作为固定长度参与上述计算，“一个月”却还不行，因为我们尚未指定从哪个日期开始。这个区别先留着，下一步看看日期是怎样进入模型的。

<a id="_1-3-5-本章时间模型的边界"></a>

本章使用普通业务系统的时间轴模型，不展开相对论或精密授时。UTC、Unix 时间与具体语言库对闰秒的处理不能直接视为同一件事；Java `Instant` 和 `Duration` 采用 Java Time-Scale。需要跨闰秒精确计量时，应核对时间源与库的尺度约定。[Java 时间尺度说明](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/Instant.html)

### 1.3.2 日历中的日期与时刻

支付流水适合记录瞬间，但生日登记通常只需要年、月、日。填写 `1995-06-12` 时，用户并没有说自己出生在当天午夜。这个值回答的是“哪一天”，称为日期。将它强行补成午夜，再换算到其他地区，可能显示为前一天；计算可以正确，额外补进去的含义却没有依据。

年、月、日如何排列，由日历系统规定。日历决定每年有哪些月份、每月有多少天，以及怎样处理闰年。同一天可以在不同历法中有不同的名称。本章采用公历，因此 `2027-03-31` 的含义无需每次重述；需要农历或其他历法时，则必须另行明确，地区时区不会替我们选择历法。

门店说“九点开门”，又是另一种信息。`09:00` 表达一天中的钟表读数，称为当地时刻。它没有指出哪一天，也没有独自表达“每天”这个重复规则。日期与当地时刻组合起来，得到 `2027-07-10T09:00` 这样的当地日期时间，可以用来记录讲师在排课表单里填写的内容。

这些对象各有独立用途。Java 的 `LocalDate` 表达日期，`LocalTime` 表达当地时刻，`LocalDateTime` 表达两者的组合。**`Local` 表示不带时区或偏移量，不表示采用本机时区**。生日、营业钟点和排课输入可以分别使用这些类型，无需为了“完整”而统一转换成瞬间。[Java 日期时间类型](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/package-summary.html)

当地日期时间可以按日历字段排序，但这个顺序不能直接用来判断跨地区事件的真实先后。东京九点和上海九点写出的时分相同，却未必对应同一个瞬间。要把它们放到共同时间轴上，我们还缺少地区的解释规则。先看一个暂时不需要这条时间轴的问题：日期增加一个月会怎样？

<a id="_1-3-3-运算关系决定算法"></a>

### 1.3.3 日历中的“增加一个月”

“从现在起再过三小时”可以从一个瞬间增加固定长度。“从今天起再过一个月”则要先找到今天在日历上的位置，再推进月份。以公历为例，2027 年 1 月 10 日到 2 月 10 日相隔 31 个日历日，2 月 10 日到 3 月 10 日相隔 28 个日历日。“一个月”没有脱离起点的固定天数，更不能预先换成固定秒数。

我们用日历量表示这种按年、月、日组成的量。Java 的 `Period` 可以表达一个月，也可以表达一年两个月零三天。它与 `Duration` 的区别在于运算依据：前者推进日历字段，后者增加时间轴上的长度。[Java `Period`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/Period.html)、[Java `Duration`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/Duration.html)

即使知道起始日期，仍可能需要选择调整规则。2027 年 1 月 31 日增加一个月，目标月份是二月，但二月没有 31 日。订阅可以约定退让到二月最后一天，也可以约定顺延到三月第一天。两个答案对应不同承诺，不能仅凭“一个月”三个字决定。

因此，**日历量表达要推进哪些单位，调整策略决定遇到不存在的日期怎么办**。日期加日历量可以得到日期，但计算需要采用明确的日历与调整规则；持续时间加在瞬间上，则不需要先知道当地几月几日。在可表示范围内，可以把这些关系记成：

```text
瞬间 + 持续时间 → 瞬间
日期 + 日历量   → 日期（采用明确的日历与调整规则）
```

“从付款起一个月后到期”同时涉及两边：付款记录是瞬间，一个月是日历量。需要先决定用哪里的当地日期或当地日期时间计算，处理月末后，再按约定得到截止瞬间。这个转换所需的时区，就是下一节要引入的对象。

至于月末退让之后，下个月应沿用退让后的日号，还是恢复原来的 31 日，是生成后续账期时的另一项选择。[1.4 节](04-calendar.md)会从计算过程说明为什么需要保留原始锚点，这里先分清参与计算的两种量。

<a id="_1-3-2-时区连接当地表示与时间轴"></a>

### 1.3.4 时区连接时间轴与当地表示

回到开篇的会员截止。上海的 `2027-04-01T00:00:00+08:00` 与 `2027-03-31T16:00:00Z` 指向同一个瞬间。前者的 `+08:00` 是 UTC 偏移量，表示当地读数比 UTC 快八小时；从当地日期时间减去这个偏移量，就得到 UTC 表示。日期跨到前一天，是换算的一部分。

已知完整的当地日期时间和偏移量，就能定位瞬间。但偏移量只解释这个读数。它没有告诉我们，同一地区半年后还是不是快八小时。地区时区为此提供随时间变化的规则：给定瞬间，查出那时的偏移量，再计算当地日期与时刻。`Asia/Shanghai` 和 `America/New_York` 是地区时区标识；后者在不同日期可能采用不同偏移量，不能用一个固定的 `-05:00` 代替。[IANA 时区数据库说明](https://data.iana.org/time-zones/tz-link.html)

两个地区现在采用相同偏移量，也不意味着它们以后会采用相同规则。**偏移量是一次换算所用的差值，地区时区提供确定这些差值的规则**。Java 用 `ZoneOffset` 和 `ZoneId` 区分两者；`OffsetDateTime` 包含当地日期时间与偏移量，`ZonedDateTime` 还关联地区时区。[Java 日期时间类型](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/package-summary.html)

从瞬间出发，在确定版本的地区规则下，可以找到相应的当地表示。反过来，用户只输入当地日期时间时，需要寻找时间轴上哪些位置会显示这个读数。钟表发生跳变时，这种反查可能没有答案，也可能不止一个。

例如，按纽约 2025 年的规则，3 月 9 日的钟表向前跳过一小时，11 月 2 日则向后拨回一小时。只看跳变前后几秒：

```text
3 月 9 日：01:59:58 → 01:59:59 → 03:00:00 → 03:00:01
11 月 2 日：01:59:58 → 01:59:59 → 01:00:00 → 01:00:01
```

春季那天没有经过当地两点半，因此填写 `02:30` 找不到对应瞬间。秋季那天的一点半则出现两次：第一次采用 `-04:00`，对应 UTC `05:30`；第二次采用 `-05:00`，对应 UTC `06:30`。相同的当地日期时间，在时间轴上占据了两个不同位置。具体边界和换算见 [1.4.1 节](04-calendar.md#sec-1-5-1)。

这说明两个转换方向并不对称。将瞬间显示为当地时间，可以按规则计算；将当地输入解析为瞬间，遇到缺口或重叠时，还需要决定拒绝、顺延，或选择其中一次。[1.6 节](06-schedules.md)会把候选瞬间的查询与业务选择分开实现。

转换也不总能原样返回。瞬间转换为某地日期后，具体时刻已经丢失；当地输入解析成瞬间后，如果只保存结果，也无法从结果推断用户原先选择了哪个地区。转换前应先确定后续还需要哪些信息。[1.7 节](07-storage.md)将据此讨论协议和存储。

<a id="_1-3-4-从基本对象构成业务规则"></a>

### 1.3.5 用这些对象表达业务

现在可以重新看会员有效期：最后有效日期是日历中的日期，失效边界是时间轴上的瞬间，二者通过业务时区及“全天有效”的规则连接起来。再加上生效瞬间和端点包含约定，才能构成前面使用的有效区间。两个边界之间的持续时间只说明长度，不能单独告诉我们会员在哪一段时间有效。

“每个工作日九点”需要另一种组合。九点由当地时刻表达，“每个工作日”由日期选择规则表达；确定具体执行瞬间，还需要地区时区和缺口、重叠的处理策略。基本类型各自保存一部分信息，完整日程由这些信息共同构成。工作日所需的节假日与调休安排属于业务日历，不能从时区名称推导出来。

表 1-2 汇总本节的基本对象，供后续选择类型时回查。类型帮助我们表达区别，选择仍从字段需要回答的问题开始。

表 1-2：基本时间对象及其 Java 类型。日期示例采用公历。

| 对象 | 回答的问题 | 示例与类型 |
| --- | --- | --- |
| 时间点 | 时间轴上的哪一刻？ | 支付完成瞬间，`Instant` |
| 持续时间 | 时间轴上的长度是多少？ | 连续三小时，`Duration` |
| 日期 | 日历上的哪一天？ | `2027-03-31`，`LocalDate` |
| 当地时刻 | 钟表上几点？ | `09:00`，`LocalTime` |
| 当地日期时间 | 日历中的哪天几点？ | `2027-07-10T09:00`，`LocalDateTime` |
| 日历量 | 推进多少年、月、日？ | 一个月，`Period` |
| UTC 偏移量 | 当地读数与 UTC 相差多少？ | `+08:00`，`ZoneOffset` |
| 地区时区 | 用哪套规则连接瞬间与当地表示？ | `America/New_York`，`ZoneId` |

类型确定之后，还需要给字段明确的业务名称。计划结束和实际结束都可以用 `Instant` 表示，但它们回答不同问题；实际晚结束半小时，不能靠覆盖同一个含糊的 `end_time` 同时保留两件事。后面的[课程设计](10-course.md)将具体区分这些依据及其派生结果。

本节把时间轴上的长度与日历中的量分开了。接下来考察“过一天”：如果当地钟表在这一天发生跳变，经过 24 小时和日历翻到下一天，会分别得到什么结果？
