# 时间来源与耗时测量

[第 1 章：时间不是一个 `datetime`](../01-time.md)

上一节把时间资格交给服务端判断：检查时刻早于截止，才允许受理。但这里仍有一个前提——服务端读到的“现在”足够准确。以报名为例，如果服务器快了五分钟，即使比较运算完全正确，报名也会提前五分钟关闭。

时间类型说明一个值表达什么，时钟则决定程序从哪里得到这个值。要让一次时间判断成立，需要沿着记录过程看清三件事：记录的是哪个事件，读数来自哪个时钟，这个时钟的误差是否会改变判断结果。

<a id="sec-1-7"></a>

## 1.9 时间来源与耗时测量

<a id="sec-1-7-1"></a>

### 1.9.1 事件含义与记录来源

一次支付可以在昨天完成扣款，今天收到回调，明天又因修改备注而更新记录。支付发生、通知接收和记录修改是三个事件，各有自己的时间。只保存一个不断变化的 `updated_at`，以后就无法用它回答钱是哪一天扣的。

因此，定义时间字段时，应同时说明**它对应哪个事件，以及由谁记录**。`occurred_at` 可以保存支付平台报告的扣款时间，`received_at` 保存本服务收到回调时读取的时间。前者是外部来源对业务事实的报告，后者是本服务对接收事件的记录；改用服务端时间不能让接收事件变成扣款事件。

例如，支付平台在 10:00:00 完成扣款，过了五秒才发出回调，本服务在 10:00:06 收到。假设两端时钟准确，`received_at - occurred_at` 得到的六秒，表示从扣款完成到回调收到的总时长，其中包含平台发送前的五秒等待。要测量回调在网络上传输了多久，还需要知道它何时发出；如果两端时钟存在偏差，即使有了发送时间，直接相减也会带入这部分误差。

来源是否可用，要结合用途判断。会员授权不能接受客户端自行提交的 `now`，否则用户调慢手机时钟就能改变资格；离线采样却可能必须保留设备报告的发生时间，才能还原采样过程。后一种场景应保留来源和必要的校验信息，并说明时间质量不足时如何处理，而非直接用接收时间覆盖。

即使值由自己的数据库生成，也要核对它记录的是哪一刻。PostgreSQL 的 `CURRENT_TIMESTAMP` 返回当前事务开始时间，`statement_timestamp()` 返回当前语句开始时间，`clock_timestamp()` 则读取调用时的当前时间。这些函数都能返回合法时间值，却不能互换。[PostgreSQL 18 当前时间函数](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)

例如事务在 23:59:58 开始，排队到 00:00:02 才检查报名资格，截止是 00:00。若规则要求按检查时刻判断，使用 `CURRENT_TIMESTAMP` 就可能错误放行，因为它仍返回截止前的事务开始时间。事务时间适合为事务内操作提供一致基准；检查需要读取当时的时间，就应选择相应接口。即使用了 `clock_timestamp()`，得到的也只是读取时刻，不能据此证明稍后的提交何时成功。

选对事件与读取位置后，仍要面对时钟本身的限制。服务端有权作出判断，不代表它的钟不会走偏。

### 1.9.2 设备怎样同步时间

应用调用系统时间接口，通常读取的是操作系统维护的本地时钟，并不会每次都向授时服务器询问。设备靠本地计时源推进时间，再通过校时修正它与参考时间的差异。

这里有两个容易混淆的量。某一刻，本机读数比参考时间快或慢多少，称为偏差；本机走速与参考走速不同，使偏差随时间积累，称为漂移。把快了两秒的钟拨回来，只修正了这一次偏差；如果它仍然走得偏快，之后还会逐渐失准。

网络时间协议（NTP）通过时间交换估计偏差。困难在于，服务端发出“现在”的那一刻，到客户端收到响应时，网络上已经过去了一段时间。直接采用响应里的时间，会把传输延迟也当作时钟差。

一次 NTP 交换使用四个读数：客户端发送时的 `t1`、服务端接收时的 `t2`、服务端发送时的 `t3`，以及客户端接收时的 `t4`。`t1`、`t4` 来自客户端时钟，`t2`、`t3` 来自服务端时钟。

![客户端与服务端分别记录四个时刻，往返间隔包含去程、服务端处理和回程](../../assets/ch01/13-ntp-exchange.svg)

图 1-8：两个参与者分别读取自己的时钟，虚线表示参与者生命线。时间从上向下，纵向不按比例；箭头的斜率不表示时钟偏差，去程与回程延迟也不要求相等。

假设这次交换期间没有时钟跳变，走速差的影响可以忽略，则有：

```text
往返网络延迟估计 = (t4 - t1) - (t3 - t2)
服务端相对客户端的偏差估计 = ((t2 - t1) + (t3 - t4)) / 2
```

第一式从客户端测得的总时间中扣除服务端处理时间，留下去程与回程之和。第二式为什么要取平均，可以把服务端比客户端快的时间记为 `θ`，去程延迟记为 `d1`，回程延迟记为 `d2`，逐项展开：

```text
t2 - t1 = θ + d1
t3 - t4 = θ - d2

偏差估计 = θ + (d1 - d2) / 2
```

当去程与回程延迟相等时，网络延迟项抵消；如果去程 80 毫秒、回程 20 毫秒，估计就比实际偏差多 30 毫秒。**一次交换不能精确分离时钟偏差与路径不对称。** 多次取样、筛选和多个时间源可以改善估计，却不能据此承诺两台机器完全同步。以上是理解 NTP 的简化推导，完整协议还包含样本处理和时钟校正算法。[RFC 5905：时间交换与偏差计算](https://www.rfc-editor.org/rfc/rfc5905.html#section-8)

得到偏差估计后，校时程序可以稍微加快或放慢时钟，让读数逐渐追上参考时间，也可以直接调整读数，造成向前或向后的跳变。具体方式取决于实现、配置和偏差大小。例如 chrony 通常渐进校正，也支持通过 `makestep` 直接跳变。因此，“开启了自动校时”既不表示时钟始终准确，也不表示它绝不会回拨。[chrony 4.4 校时说明](https://chrony-project.org/doc/4.4/chronyc.html#makestep)

同步中断后，本地时钟仍继续运行，误差却可能继续累积；上游时间源本身也需要可信。普通业务应用通常让操作系统或基础设施管理校时，再检查其时间质量是否满足业务要求。时区配置是另一件事：它决定当地如何显示这个读数，切换到 `Asia/Shanghai` 不会把快了五分钟的钟校准。

### 1.9.3 钟表读数之差为何不一定是耗时

校时能够改善“现在是哪一刻”的估计，却也让两次读数之差不再可靠地代表经过长度。用户实际等了两秒，如果期间系统钟表向后调整五秒，结束减开始就会得到负三秒。

表 1-5：同一请求期间钟表回拨五秒。右列是同一本地单调计时源的示意读数。

| 读数或差值 | 系统钟表 | 本地单调计时 |
| --- | --- | --- |
| 请求开始 | 10:00:00 | 100 秒 |
| 请求结束 | 09:59:57 | 102 秒 |
| 结束减开始 | −3 秒 | 2 秒 |

系统钟表提供的钟表时间（wall-clock time）可以对应日历，用来记录事件、展示日期和比较长期截止。单调时钟（monotonic clock）提供不因日历钟表调整而回拨的计时依据，用来测量同一计时源中的经过长度。它的起点通常没有业务含义，重要的是两次读数的差。

例如 Java 的 `System.nanoTime()` 用于测量耗时，同一 JVM 内的调用共享起点；不能假定另一 JVM 或重启后的实例具有相同起点。返回值以纳秒表示，也不意味着每纳秒都会产生不同读数，更不代表测量误差只有一纳秒。[Java 25 `nanoTime`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.html#nanoTime())

```text
started_at = wall_clock.now()       // 日志：请求何时开始
begin      = monotonic_clock.now()  // 测量：从这里开始计时

执行请求

elapsed = monotonic_clock.now() - begin
```

这里的两个值各有用途：`started_at` 用来关联日历上的事件，`elapsed` 用来描述本次请求花了多久。**记录事件时刻与测量耗时，应分别选择适合的时钟。** 单调读数不能直接作为跨机器时间戳，也不适合原样保存为重启后仍要使用的会员截止。

同样的选择适用于超时。进程内一次操作共有三秒等待预算，查库已经消耗一秒，后续就只剩两秒，应用可以用单调计时计算剩余预算；若改用钟表差值，回拨可能延长等待，前跳可能提前耗尽预算。等待何时结束、如何取消工作和传播预算，在[第 24 章](../../part-03-repetition/09-timeouts.md)继续展开。

单调性只约束读数的方向，不保证走速绝对准确。休眠是否计入经过时间，也要核对具体平台与 API：电脑休眠十分钟后，业务若要求三秒预算已经耗尽，所选计时源就必须符合这个要求。换一个计时 API 之前，应先明确要测量的是哪种经过长度。

### 1.9.4 时钟有误差，判断能有多准确

单机耗时可以避开钟表跳变，但跨机器事件与长期截止仍需要钟表时间。此时应明确误差怎样进入结果，而不能因为读数都采用 UTC 就忽略它。

在同一参考时间尺度下，把时钟读数写成“实际时刻 + 本机误差”，两台机器的记录相减便得到：

```text
接收读数 - 发送读数
= 实际传输时间 + 接收端误差 - 发送端误差
```

假设 A 发送后经过 100 毫秒，B 才收到；A 的钟快 200 毫秒，B 的钟慢 200 毫秒，读数差就是 `100 - 200 - 200 = -300` 毫秒。消息没有先到后发，负值来自两端的时钟误差。消息关联和收发关系仍能说明因果，但单靠这两个时间戳不能精确测出单向传输耗时。跨机顺序的进一步讨论见[第 31 章](../../part-05-distribution/19-ordering.md)。

截止比较也会受误差影响。假设截止 `E` 是同一尺度下已确定的瞬间，当前读数为 `c`，并且有依据保证此刻误差不超过 `ε`，实际时刻就位于 `[c - ε, c + ε]`。对于“严格早于截止”这个条件，可以分成三种情况：

- `c + ε < E`：即使实际时间落在区间最晚处，也仍早于截止。
- `c - ε >= E`：即使实际时间落在区间最早处，也已经到达或越过截止。
- 其余情况：误差区间跨过截止，现有读数不足以确定是否满足条件。

![误差区间完全早于截止时确定未到期，跨过截止时无法确定，最早端到达截止时确定已到期](../../assets/ch01/14-clock-uncertainty.svg)

图 1-9：在误差上界成立的前提下，粗线表示实际时刻的可能范围，实心点表示包含端点，竖虚线对齐截止 E。三行分别表示三种读数情况，第三行画出最早端恰好等于截止的情形；横向不按比例。

例如截止是 12:00:00，读数是 11:59:59.800，误差上界为 500 毫秒，那么实际时刻可能位于 11:59:59.300 到 12:00:00.300 之间。代码执行 `c < E` 会返回真，但这并不能保证实际检查发生在截止前。

**临近截止时，误差会变成业务必须处理的不确定性。** 若要求资格检查实际发生在截止前，可仅在 `c + ε < E` 时通过，代价是部分原本仍来得及的请求也会被拒绝。若选择有限容忍来减少误拒，则要承认受理范围可能越过原截止。两种选择改变的是承诺，不能靠多保留几位小数消除差别。

上述推导依赖一个真实成立的误差上界。监测工具最近一次报告的偏差，不能直接充当这样的保证；失去同步后，也不能无限沿用旧估计。若连误差范围都无法确认，就不能继续声称判断具有同样的精度。

### 1.9.5 时间不准会让哪些判断失效

误差模型可以用来解释实际故障，但处理方式取决于时间参与了什么判断。超时测量可以改用单调计时；证书有效期、提醒计划和日报归属仍要使用日历上的时间，不能一起替换。

TLS 证书验证需要检查验证方认为的当前时间是否处于证书有效期内。客户端时钟过慢，可能把已经生效的服务端证书判为尚未生效；过快则可能把仍有效的证书判为过期。双向 TLS 中，服务端验证客户端证书时也依赖自己的时钟。这里要检查的是验证方的时间，不一定是证书持有方的时间。RFC 5280 规定证书有效期包含 `notBefore` 与 `notAfter` 两端，不能直接套用本章业务示例的半开区间。[RFC 5280：证书有效期](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.1.2.5)

登录令牌也有类似依赖。JWT 的 `exp` 要求当前时间严格早于过期边界，`nbf` 要求当前时间已经到达起始边界；签发方与验证方有偏差时，刚签发的令牌也可能被拒绝。规范允许为小量时钟偏差设置有限容忍，但容忍会扩大可接受的时间范围。具体放宽哪一端、放宽多少，需要按验证配置确认。[RFC 7519：`exp` 与 `nbf`](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1.4)

到点执行则多了一项责任：记录事情是否已经做过。提醒计划在 10:00 执行，钟表从 09:59 跳到 10:01，只匹配“当前恰好是 10:00”的实现就可能漏掉它；查询“已到期且未执行”的计划可以发现迟到任务，再按策略补跑或跳过。钟表回拨后是否重复执行，则取决于是否保留并检查执行事实。**时钟提供到期条件，执行记录说明计划是否已经处理。** 仅有时间比较，无法保证任务只执行一次。

权限关闭也有相似之处。时钟回拨后，`now < expires_at` 可能从假重新变真。如果业务承诺“已经关闭后绝不重新开放”，就要保留关闭事实，并让后续检查遵守这个终态。前文的有效期计算与状态记录在这里各有职责：前者判断当前是否满足时间条件，后者保留不可逆的业务结果。

日报和日志分析还要区分时钟错误与时区错误。设备时钟准确、业务时区选错，事件可能被分到错误日期；时区正确、时钟慢了几分钟，午夜附近的事件也可能被记到前一天。前者需要修正日期归属规则，后者需要处理时间来源。修改展示时区不会修复证书验证所使用的当前时间，也不会校准报名服务的时钟。

### 1.9.6 如何发现失准，并验证处理方式

“校时进程还活着”只能说明程序在运行，不能说明时间仍满足业务要求。监测至少需要结合可用时间源、最近成功取样时间、偏差及误差估计。例如 chrony 的 `tracking` 提供参考时间、系统时间差、频率偏差和根离散度等信息，`sources` 提供来源状态；这些指标含义不同，应按工具定义解释，而不能只挑一个最小的数当作当前精度。[chrony 4.4 监测接口](https://chrony-project.org/doc/4.4/chronyc.html#tracking)

**误差要求应落实到具体操作及其失准策略。** 客户端课程倒计时不承担最终授权，可以在时间不可靠时重新向服务端获取依据并提示用户；严格截止的报名服务则要约定，时间质量不满足要求时，是暂停新受理，还是转交另一个时间质量可检查的服务。前者降低可用性，后者增加依赖。阈值、受影响操作和恢复条件应一并定义，单纯告警并不会改变错误判断。

测试应当能分别控制钟表时间和单调计时。让单调读数前进两秒，同时让钟表回拨五秒，耗时仍应为两秒；让客户端快十分钟，服务端报名结果不应随之变化；在截止附近分别构造误差区间完全位于截止前、跨过截止和完全位于截止后的情况，检查受理策略是否符合约定。再模拟同步中断、健康条件不再满足，确认应用执行了暂停或转交，而不只是写下一条告警。时间注入与相关实验见[权限与时钟实验](../../../examples/ch01-time/deep-dive.md#validity-and-clock-tests)。

到点执行需要另一组验证：让钟表向前跳过计划点，检查迟到任务如何处理；执行后再把钟表拨回，检查同一计划是否会重复产生业务效果。这些检查涉及调度器、执行记录及失败恢复，单独验证时间库不能覆盖它们。

应用注入的时钟通常也无法控制 TLS 库内部的时间读取。证书有效期应通过支持指定验证时间的测试接口，或在隔离环境中验证，分别覆盖尚未生效、有效和过期。这里列出的是实现时的验证要求，不代表本书已经运行过真实 NTP 或 TLS 故障实验。

回到报名截止：我们现在既能说明检查发生在哪一步，也能说明检查依赖谁的时钟，以及误差过大时如何处理。下一节把这些选择与前面的日历、存储和生命周期规则放到同一个课程设计中，检验它们能否共同兑现需求。
