# 时间来源与耗时测量

[第 1 章：时间不是一个 datetime](../01-time.md)

一个时间值即使类型正确、传输无误，也未必能支持我们想要的结论。它记录哪个事件、由谁观察、时钟有什么性质，是彼此独立的问题。前面讨论了怎样保存和计算时间，现在要确认这些时间究竟是怎样得来的。

<a id="sec-1-7"></a>

## 1.9 时间来源与耗时测量

<a id="sec-1-7-1"></a>

### 1.9.1 事件含义与记录来源

一次支付可以在昨天完成扣款，今天收到回调，明天又因修改备注而更新记录。支付发生、通知接收和记录修改是三个事件，分别对应自己的时间。若只保存会不断变化的 `updated_at`，就无法再从中回答钱是哪一天扣的。

字段应与事件和来源一起定义。`occurred_at` 可以是设备或支付平台报告的发生时间，`received_at` 是接收服务记录的到达时间。两者差值包含传输与等待，也可能包含源时钟误差、离线缓存和接收队列延迟。因此，**减法在数值上成立，并不意味着结果就是网络耗时**。

对事件时间是否可信，应按来源判断。服务端控制会员权限时，客户端自行提交的 `now` 不能用于最终授权，否则调慢手机时钟就能改变权益。设备离线采样的发生时间却可能是业务需要的信息，应保留来源及必要的校验依据，而非一律用接收时间覆盖。客户端倒计时估计与设备时间校正集中见[权限与时钟实验](../../../examples/ch01-time/deep-dive.md#validity-and-clock-tests)。

数据库默认时间也要按具体语义使用。PostgreSQL 的 `CURRENT_TIMESTAMP` 表示当前事务开始时间，`statement_timestamp()` 表示当前语句开始时间，`clock_timestamp()` 读取实际当前时间。事务持续一段时间后，前一个值仍然不等于此刻，更不自动等于提交成功时刻。[PostgreSQL 当前时间函数](https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)

选择函数的依据应是要记录的事件。需要事务内统一时间基准时，事务开始时间可能合适；需要观察执行期间的钟表读数时，则应使用相应时间源。无论选择哪种函数，它都不能自行证明远端支付平台何时完成扣款。

<a id="sec-1-7-2"></a>

### 1.9.2 钟表读数之差为何不一定是耗时

钟表时间（wall-clock time）把事件放在可与日历对应的时间轴上，适合记录、展示和持久化截止。它可能被人工调整或校时机制修正。若用两次钟表读数相减，结果除了实际经过的长度，还会包含期间发生的时钟调整。

例如请求运行两秒，系统钟表期间向后调整五秒，读数差便是 `2 - 5 = -3` 秒。接口没有倒着运行，变化的是测量基准。向前跳变同样会放大耗时，单位写成纳秒也无法纠正这种错误。

表 1-5：同一请求期间钟表回拨五秒。右列是同一本地单调计时源的示意读数。

| 读数或差值 | 系统钟表 | 本地单调计时 |
| --- | --- | --- |
| 请求开始 | 10:00:00 | 100 秒 |
| 请求结束 | 09:59:57 | 102 秒 |
| 结束减开始 | −3 秒 | 2 秒 |

单调时钟（monotonic clock）提供不随日历钟表调整而回拨的计时依据，适合测量同一计时源中的经过长度。Java 的 `System.nanoTime()` 用于这个目的；其起点任意，读数差在同一 JVM 内才具有约定意义，纳秒单位也不代表纳秒分辨率或精度。[Java `nanoTime`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.html#nanoTime())

```text
started_at = wall_clock.now()       // 记录请求在何时开始
begin      = monotonic_clock.now()  // 建立本地计时起点

执行请求

elapsed = monotonic_clock.now() - begin
```

这里保留两个值，是因为**记录和测量承担不同任务**。单调读数没有通用的日历含义，不能当作事件时间戳交给另一台机器，也不能默认重启后仍共享同一起点。不同平台对休眠期间是否累计的约定也可能不同，选择运行环境的计时 API 时需要核对。

这种区别同样决定截止如何保存。会员有效期需要跨进程重启保留，通常保存已确认的时间点；进程内三秒等待预算需要累计已经消耗的长度，适合单调计时。若查库已经用掉一秒，后续最多还剩两秒，不能重新获得完整三秒。预算传播与等待结束后的处理在[第 9 章](../../part-03-repetition/09-timeouts.md)继续展开。

### 1.9.3 时钟有误差，判断能有多准确

采用服务端时间解决了谁有权提供授权依据的问题，并不保证服务器绝对准确。两台受控机器仍可能存在偏差，单台机器也可能发生校时调整。因此，应把“**可信来源”和“足够准确**”作为两个条件检查。

若以同一参考尺度观察，记录下来的时刻可以看作实际发生时刻加上该时钟的误差。两个来源的读数相减，除事件间隔外还包含误差之差。A 记录发送，B 记录接收，即使接收真实发生在后，B 的钟足够慢时，日志仍可能显示接收更早。时间戳都合法，顺序推断却没有足够依据。

边界判断也存在类似限制。若确有可靠的误差界限，在误差范围覆盖截止的时刻，仅凭本地读数未必能证明请求处在边界哪一侧。系统需要选择判定方及策略：按指定权威来源判定，或者在不确定范围内按业务决定保守拒绝或容忍。缺少经过验证的误差界限时，不能随意写一个两秒常量就声称问题已解决。

这里还涉及时间条件是否允许逆转。钟表回拨后，原本越过截止的比较可能再次满足范围；若业务承诺“完成关闭后绝不重新开放”，就需要持久化关闭事实及相应状态约束。单调计时不能简单替代所有长期截止，状态模型也不能代替时间源管理，两者解决不同的限制。

校时、偏差监控与来源约定提供运行基础，跨机因果关系和更强的顺序保证需要其他机制，见[第 21 章](../../part-05-distribution/21-distributed-time.md)。所以，读到一个时间戳时，除了看类型和字段名，还要问它由谁记录、可能有多大误差。能比较两个数值，并不等于能确定两件事的真实先后。
