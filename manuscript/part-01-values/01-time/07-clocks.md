# “现在”从哪里来

[第 1 章：时间不是一个 datetime](../01-time.md)

边界、存取和日历规则已经明确，比较时却还有一个输入需要检查：“现在”。时间来自哪里，以及它适合记录事件还是测量耗时，会影响最后的判断。

<a id="sec-1-7"></a>

## 1.7 时间存对了，“现在”可靠吗

会员截止、日历规则和接口含义已经明确。但比较还需要另一个输入：`now`。它由谁提供，又适合回答什么问题？

<a id="sec-1-7-1"></a>

### 1.7.1 手机时间、事件时间与记录时间

用户把手机日期调回去年，不应该获得更长的会员。业务权限由服务端控制时，客户端提交的 `now` 不能参与最终授权。客户端可以显示倒计时，真正提交操作时仍由服务端判断。

设备昨天采样、今天联网，却不能简单丢掉昨天的时间。可以分别保存设备提供的 `occurred_at` 和服务端记录的 `received_at`。两者差值可能来自离线等待，也可能来自设备时钟错误，不能直接当作网络延迟。倒计时估计与设备校正见[权限与时钟实验](../../../examples/ch01-time/deep-dive.md#validity-and-clock-tests)。

两个 `Instant` 都可以比较，类型却看不出一个来自支付平台，另一个来自设备乱设的时钟。类型帮助区分类别，事实来源仍需单独说明。

换成支付回调也一样。昨天扣款，今天收到通知，明天修正备注，这三个动作可以对应三个不同的时间。若 `updated_at` 会在修改备注时自动更新，它记录的就是行修改，无法再用来回答钱是哪天扣的。

数据库生成的时间也有具体含义。例如 PostgreSQL 的 `CURRENT_TIMESTAMP` 表示事务开始时间；事务运行一段时间后再写入，它仍不是那一刻的提交时间。用作创建记录的默认值可以很方便，但不能据此证明支付平台完成扣款的时刻。[PostgreSQL 当前日期时间函数](https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)

<a id="sec-1-7-2"></a>

### 1.7.2 请求耗时为什么会变成负数

记录“请求在几点开始”，需要钟表时间。测量“请求用了多久”，最好不要使用同一把尺子。

系统钟表可能被人工调整，也可能被校时机制修正。如果在请求开始和结束各取一次日期时间再相减，期间发生时钟跳变，结果可能偏大，甚至为负数。这个接口并没有倒着运行，是计时的基准变了。

假设请求实际运行两秒，期间系统钟表向后调整五秒，两次读数就会得到下面的差别。右列是同一个本地单调时钟的示意读数，起点没有日历含义。

表 1-4：系统钟表回拨五秒后的两种耗时计算。

| 读数或差值 | 系统钟表 | 同一本地单调时钟 |
| --- | --- | --- |
| 请求开始 | 10:00:00 | 100 秒 |
| 请求结束 | 09:59:57 | 102 秒 |
| 结束减开始 | −3 秒 | 2 秒 |

单调时钟（monotonic clock）用于测量经过的长度，不跟随钟表日期的调整。Java 中可以使用 `System.nanoTime()` 读取本地计时源：读数的起点任意，有意义的是同一 JVM 内两次读取的差值。单位是纳秒，但不保证计时源每纳秒更新一次。[Java 本地计时接口](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.html#nanoTime())

```text
started_at = wall_clock.now()       // 留给记录与展示
begin      = monotonic_clock.now()  // 留给本地计时

执行请求

elapsed = monotonic_clock.now() - begin
```

进程内的等待预算也应累计已经花掉的时间。例如总共允许三秒，查数据库已经用掉一秒，调用远端就最多再等两秒。[第 9 章](../../part-03-repetition/09-timeouts.md)将接着讨论共同预算与等待结束后的结果。

但单调时钟值不是另一种可持久化时间戳。不要把它发给另一台机器，也不要写进数据库后等重启再解释，它没有跨这些边界的通用日历含义。不同平台对休眠期间是否计时也可能不同，应按实际运行环境选择计时 API。

会员到期时间要在重启后仍然有效，因此仍应持久化成一个时间点。进程内等待网络响应则适合用单调时钟。二者都叫“截止时间”，却面对不同的生命周期，不能只因为名字相似就共用一种存法。

### 1.7.3 服务端可控，不等于时钟绝对准确

“服务端时间”只是把信任边界放到我们控制的一侧，多台服务仍可能存在偏差。A 记录发送，B 稍后记录接收，如果 B 的钟慢一些，日志里就可能出现接收早于发送。

校时与偏差监控是基础工作，涉及到期争议还应指定事实来源和判定方。普通跨机时间戳不能单独证明两个事件的因果顺序。[第 21 章](../../part-05-distribution/21-distributed-time.md)将接着讨论多机误差和集中判定的代价。
