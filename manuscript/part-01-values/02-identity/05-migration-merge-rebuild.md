# 迁移、合并与重建：身份如何穿过变化？

[← 表示与暴露](04-representation-exposure.md) · [返回第 2 章](../02-identity.md)

订单服务运行了几年，数据库开始按区域拆分。上海库里的订单搬到华东分片，内部主键从 `17` 变成了 `9042`；用户手里的订单链接、客服工单和支付对账记录，却不能跟着数据库的行号一起失效。

这不是一次普通的数据搬运。系统要回答的是：旧记录和新记录是不是同一个业务对象？旧链接、旧日志和外部系统里的编号怎样找到它？迁移过程中，旧库和新库同时接收请求时，哪一边的写入才算数？

前面已经得到三个判断：唯一性解决“会不会撞”，稳定性解决“搬家后是不是同一个”，公开表示决定“别人怎样引用它”。本节把这三个判断放进真实变化里。

## 2.5 迁移、合并与重建：身份如何穿过变化？

### 2.5.1 先把身份和位置拆开

假设订单原来存储在单库：

```text
旧库：internal_id = 17
      entity_id   = order-A
      order_no    = SH-2026-001048
```

迁移到分片后，记录可能变成：

```text
新库：internal_id = 9042
      entity_id   = order-A
      order_no    = SH-2026-001048
```

`internal_id` 只负责当前数据库里的定位，`entity_id` 负责跨位置识别订单，`order_no` 负责用户和业务流程中的引用。**迁移改变了存储位置，不应悄悄创建第二个业务身份。** 如果新库生成了新的 `entity_id`，支付系统和历史日志就无法直接确认这两条记录属于同一订单。

因此，迁移前要先列出每个字段的职责，而不是看到一列叫 `id` 就把它全部复制或全部重生成：

| 标识或字段 | 迁移时的主要问题 | 通常的处理 |
| --- | --- | --- |
| 本地内部主键 | 新库是否允许重新编号 | 可以变化，但不能拿它证明业务身份变化 |
| 稳定实体 ID | 新旧记录是否指向同一对象 | 保留原值，或建立可验证的映射 |
| 公开订单号 | 用户的旧引用是否继续有效 | 保留原值，必要时维护旧号解析 |
| 分片或租户位置 | 当前记录在哪里 | 作为新的位置属性更新 |

如果公开订单号本身就是稳定实体 ID，映射层可以更简单；如果它只是某个租户内的业务编号，就不能脱离租户或来源单独使用。标识的作用域必须和查找路径一起保存。

### 2.5.2 旧号到新号的映射不是临时脚本

有些迁移无法保留稳定 ID：旧系统的订单只有自增主键，或者外部系统已经使用了另一种编号。此时需要显式的映射关系：

```text
来源系统   来源类型   旧标识       新实体 ID   映射状态
legacy-a   order      17           order-A     confirmed
legacy-a   order      18           order-B     pending
```

这张表不是迁移脚本的中间产物。只要旧链接、旧文件、旧对账单或历史事件仍可能出现，它就承担着把旧证据接回当前对象的责任。映射至少要能说明来源系统、来源类型、旧标识、新身份和确认状态；需要追责或审计时，还应记录迁移批次、时间和确认依据。

映射关系也有方向和生命周期。旧标识可以解析到新身份，但新身份不应反过来随意猜测旧来源；一个旧标识如果曾经被错误导入，就不能靠覆盖一行来抹掉这次判断。对外接口可以继续接受旧号并返回重定向或兼容响应，内部存储则使用新身份。何时停止解析旧号，是兼容承诺的一部分，不能由“迁移脚本跑完了”自动决定。

### 2.5.3 合并时，重复编号不等于同一个对象

两个租户合并到同一套系统，双方都存在 `customer_id = 7`：

```text
租户甲：customer_id = 7，姓名：李宁
租户乙：customer_id = 7，姓名：李宁
```

相同的编号和姓名都不能证明这是同一个客户。可能是两个人，也可能是同一人在两个租户中的账户。直接删除一条记录，会把订单、授权和历史操作一起归错；直接给两条记录拼接前缀，又可能把本来应该合并的账户永远分开。

合并需要先区分三种关系：

- **同一对象**：两条来源记录确认指向同一个客户，建立一个新的规范身份，并保留来源别名。
- **不同对象**：两条记录只是字段相同，分配不同身份，不能共享订单和授权。
- **暂时无法判断**：先保留两条记录和待确认状态，不用猜测结果驱动自动合并。

确认同一对象后，可以维护别名表：

```text
规范身份：customer-A
来源别名：tenant-a/customer/7
来源别名：tenant-b/customer/7
```

别名适合表示“过去怎样称呼这个对象”，不适合把多个当前对象压成一个编号。查询旧系统数据时，别名可以帮助定位规范身份；创建新数据时，应使用规范身份，避免别名继续扩散到新的接口和表中。

合并依据也应成为数据的一部分。人工确认、外部唯一凭证、用户主动绑定和高置信度匹配，承担的证据强度不同。没有足够证据时保留冲突，比生成一个看似整洁却无法解释的客户档案更可靠。

### 2.5.4 外部导入要保留来源身份

外部系统导入订单或客户时，不能只把对方的 `id` 写进本系统的主键列。不同来源很可能都使用从 `1` 开始的自增值；即使今天只有一个来源，明天增加第二个来源就会撞号。

更稳妥的记录方式是把来源作为身份的一部分：

```text
source_system = partner-x
source_type   = order
source_id     = 3819
entity_id     = order-A
```

`source_system + source_type + source_id` 可以作为导入记录的幂等键：同一来源的同一对象重复导入时，系统找到原来的映射，而不是再创建一笔订单。`entity_id` 是本系统的规范身份，来源标识则保留外部系统中的原始称呼。两者都可能需要展示给排查人员，但不应互相替代。

外部对象后来更新时，系统还要知道谁拥有哪个字段。导入只写入本系统负责的字段，或者记录来源版本后再决定是否覆盖；否则，一次重复导入就可能把本地人工修改恢复成旧值。字段所有权和冲突合并属于后续数据协作问题，本节只强调：来源标识必须留下，不能把来源信息抹在一次转换里。

### 2.5.5 双读双写不是“多写一次”

迁移期间经常出现旧库和新库同时在线。一个常见阶段如下：

```text
请求
  ↓
路由：根据稳定实体 ID 或映射表选择位置
  ├─ 读：优先新库，必要时回退旧库
  └─ 写：写入主库，并把变更传播到另一边
```

这里最容易被忽略的是“谁是主库”。如果两边都能独立接受写入，就必须处理乱序、重复和冲突；如果只有一边是权威写入，另一边的更新就应被视为复制或迁移动作。双写不是天然的一致性保证，只是把迁移窗口中的两个存储都纳入了责任范围。

迁移方案至少要明确几个边界：切换前产生的写入如何追上新库，切换时正在处理的请求由谁完成，读到新旧两份不同记录时以什么版本或时间点为准，回滚时哪些变更可以安全地写回旧库。没有这些约定，“双写成功”只说明两个写操作返回了成功，不说明它们记录了同一件事。

可以先设置一个短暂的兼容阶段：旧入口仍接受请求，但通过映射定位规范身份；新入口只写新库；旧库的变化以变更日志或明确的同步任务追到新库。等到读路径、写路径和对账结果都满足切换条件，再停止旧写入。切换后仍保留只读映射，直到旧链接和历史任务不再需要。

### 2.5.6 灾备重建：记录可以重建，证据不能丢

灾备恢复可能把数据写进一套全新的数据库。新库的内部主键、索引和分片位置都可能变化，但订单身份和历史引用仍要可追溯：

```text
备份记录：entity_id = order-A，internal_id = 17
恢复记录：entity_id = order-A，internal_id = 310
```

恢复流程应优先依据稳定身份或可信映射重建关系，而不是按导入顺序重新编号后再猜测。订单与支付、发货、退款记录之间的关联，也应使用各自稳定的实体或外部交易标识恢复；不能因为两张表恰好都出现 `17` 就重新连在一起。

恢复后需要验证的不只是“行数相同”。至少要检查：旧公开引用能否找到同一对象，跨系统关联是否仍指向原记录，重复恢复是否不会创建第二个实体，已撤销的别名或分享授权是否保持原状态。恢复是一种身份测试：它检验系统保存的是业务关系，还是某次数据库布局的偶然结果。

如果备份本身来自多个时间点，还要标记恢复边界。订单记录可能已经恢复，支付记录却只恢复到更早版本；此时系统不能把“找不到支付记录”解释成“订单从未支付”。缺失、延迟和未知状态应保留为可观察结果，等待对账或补偿流程处理。

### 2.5.7 用迁移结果检查设计是否自洽

一次迁移完成后，可以用下面的问题验收身份设计：

| 检查问题 | 如果答案是否定的，暴露了什么问题 |
| --- | --- |
| 旧链接能找到原对象吗？ | 公开标识没有稳定策略，或映射已丢失 |
| 新旧内部主键变化后，支付和审计记录仍能关联吗？ | 把存储位置误当成业务身份 |
| 两个来源的相同编号能解释为何合并或保持分开吗？ | 缺少来源标识和合并依据 |
| 重复导入会复用原实体吗？ | 没有来源组合键或导入映射 |
| 切换期间的写入能判断谁是权威吗？ | 双读双写边界没有定义 |
| 灾备恢复后，未知和缺失状态仍可区分吗？ | 把不完整证据误当成业务事实 |

这些问题的共同点是：它们都要求系统保存“这个对象是谁”以及“我们为什么认为它是这个对象”的证据。迁移不是给旧 ID 换个新名字，而是让身份、位置、来源和历史引用继续保持可以解释的关系。

本节可以归结为一句话：**映射解决旧证据怎样找到新位置，来源标识解决相同编号来自哪里，稳定实体 ID 解决变化前后是不是同一个对象。** 下一节把视线从存储变化转到一次正在发生的操作：一个支付请求里，实体 ID、请求 ID、幂等键和外部交易号为什么也不能互相替代。
