# 生成方式：自增、随机与按时间排序各保护什么？

[← 唯一性与稳定性](02-uniqueness-stability.md) · [返回第 2 章](../02-identity.md)

上一节已经确定：唯一性必须带着范围，稳定性必须带着生命周期。现在才适合比较 ID 的生成方式。

这里不先问“哪一种 ID 最先进”，而是对每种方案都问四个问题：

1. 它在哪个范围内保证不冲突？
2. 多个生成者需要怎样协调？
3. 它是否带有顺序或可预测性？
4. 为了得到这些性质，系统新增了哪些状态和故障模式？

没有一种生成方式同时在所有方面占优。选择的对象不是一个字符串格式，而是一组业务保证。

## 2.3 生成方式：自增、随机与按时间排序各保护什么？

### 2.3.1 自增整数：简单的局部秩序

在单个数据库中，自增整数通常是最直接的选择：插入一行时由数据库分配下一个值，主键索引紧凑，按编号查询和排序也很方便。

```text
订单表：
1001  → 1002  → 1003  → 1004
```

它适合这样的前提：生成动作集中在一个数据库或一个明确的分配服务中，编号只需要在这个范围内唯一，业务也不把编号当作跨系统身份。

但自增值提供的顺序很有限。`1004` 比 `1003` 大，只能说明它在同一分配序列中较晚取得，不能证明对应订单一定较晚提交、较晚支付，甚至不能证明它们的业务事件发生顺序。事务回滚、并发提交和异步处理都可能让编号顺序与业务时间分离。

当系统扩展到多个数据库或多个区域时，独立自增序列会产生相同的值：

```text
区域 A：order_id = 1001
区域 B：order_id = 1001
```

要继续使用自增形式，就需要额外设计，例如分配不同号段、使用区域前缀，或增加一个统一的编号服务。这样做可以满足新的唯一性范围，却也引入协调、号段耗尽、服务不可用和迁移规则等问题。自增整数并没有自动变成全局身份，只是把分配责任放在了某个中心或约定上。

另一个代价是可预测性。连续编号可能暴露记录规模，也可能让调用者猜出相邻对象的地址。因此，内部主键适合直接定位记录，不代表它适合直接放进所有公开 URL 或授权接口。公开暴露和权限检查要在后文单独讨论。

### 2.3.2 UUID：减少协调，接受更长的表示

UUID 的价值在于：多个生成者可以在不访问同一个自增序列的情况下生成标识。只要采用的版本和生成规则满足约定，设备、服务或区域就能独立创建候选值，再把它用于跨边界关联。

常见版本的性质并不相同：

- UUID v4 主要使用随机或伪随机位，通常不提供可依赖的时间顺序。
- UUID v7 将时间信息放入高位，并保留随机部分，适合需要大致按生成时间排序的场景。
- 其他版本可能根据名称或节点信息生成，不能笼统地把所有 UUID 都称为“随机 ID”。

因此，使用 UUID 时至少要写清楚版本、随机源和唯一性假设。把一个字符串写成 UUID 格式，并不会自动获得跨系统唯一性；如果随机源质量不足、实现错误或生成空间被截断，冲突仍然可能发生。

UUID 的代价主要体现在表示和存储上：字符串更长，人工口述困难；无序 UUID v4 在某些索引结构中会带来更分散的写入位置；日志、缓存键和消息体也会变大。二进制存储、合适的索引和可读的外部编号可以缓解这些问题，但不会改变它们是设计成本。

UUID 也不等于匿名。v4 不直接暴露时间，v7 则会泄露粗略的生成时间；两者都不能替代认证、授权或敏感信息保护。

### 2.3.3 按时间排序的结构化 ID：把协调责任写进格式

Snowflake 一类的结构化 ID，通常把时间片、节点编号和序列号组合到一个整数中：

```text
时间片       节点       序列
高位 ─────── 中间 ───── 低位
```

它希望同时得到两种性质：多个节点可以独立生成，生成结果又大致按时间递增。对于高写入量系统，这种布局可能比完全随机的长字符串更适合索引和日志检索。

但这些性质依赖一组运行约束：

- 节点编号必须在同一时刻不重复，否则不同节点可能生成相同值。
- 单个节点在同一时间片内的序列空间不能耗尽；耗尽后要等待、扩容或改变分配规则。
- 时钟回拨需要有明确处理方式。暂停发号、等待时钟追上、切换纪元或拒绝生成，都会影响可用性和实现复杂度。
- 位宽和纪元决定可使用多久；时间字段耗尽后需要迁移方案。

“按时间排序”也只是生成时间的近似顺序。不同机器的时钟可能有偏差，网络延迟和事务提交顺序也会重新排列事件。这个 ID 可以帮助索引和分页，却不能单独证明两个业务动作的先后关系。

### 2.3.4 业务编号：为沟通设计的另一种标识

“订单号”“工单号”“发票号”通常是业务编号。它们可能包含地区、年份、渠道或校验位，目标是方便客服、财务和用户沟通：

```text
内部实体 ID：7f3c…9a21
公开订单号：SH-2026-001048
```

业务编号不一定适合承担内部身份。它可能需要按业务规则重新编排，也可能因为隐私、合规或产品调整而改变显示格式。更稳妥的设计通常是把它与内部实体 ID 分开，并明确两者之间的映射。

业务编号的可读性也会带来约束：是否允许跳号，是否必须连续，是否按区域分别编号，是否可以回收，是否需要校验位，旧编号是否永久有效。这些问题没有统一答案，但都必须由业务规则明确，不能从“它看起来像一个编号”推断。

### 2.3.5 放在同一张表里比较

| 方案 | 主要优势 | 主要代价 | 更适合的边界 |
| --- | --- | --- | --- |
| 自增整数 | 简单、紧凑、局部顺序清晰 | 需要中心分配，容易暴露规模，跨库合并麻烦 | 单库内部主键 |
| UUID v4 | 生成者之间少协调，跨边界方便 | 长度、可读性、索引局部性 | 分布式实体身份、无需排序的场景 |
| UUID v7 | 保留分布式生成能力，带大致时间顺序 | 仍较长，时间信息有暴露，顺序不是业务顺序 | 分布式实体身份、需要时间友好索引的场景 |
| Snowflake 类 | 整数表示、近似递增、可分布式生成 | 节点配置、时钟回拨、序列耗尽和位宽规划 | 高写入量、需要近似时间排序的内部系统 |
| 业务编号 | 方便人和业务流程使用 | 规则复杂，稳定性和连续性要求高 | 客服、财务、用户可见引用 |

这张表只能帮助缩小选择范围，不能替代边界声明。例如，系统可以用自增整数作为单库主键，用 UUID 作为跨服务实体 ID，再用业务编号服务用户；也可以只使用一个值，但必须接受它同时受到这些场景的约束。

### 2.3.6 选择前先写出保证

在确定格式之前，先写一份小的设计声明：

- 生成者有几个，未来会不会增加？
- 唯一性需要覆盖哪些数据库、租户、区域和系统？
- 是否需要按生成时间大致排序？如果需要，排序是否只是索引便利，还是被误当成业务顺序？
- 标识是否会出现在 URL、日志、导出文件或用户界面？
- 生成服务不可用、节点重复、随机源异常或时钟回拨时，系统要怎样处理？
- 这个值要稳定到什么时候，迁移后是否仍需保留？

写清这些保证后，算法名称只是实现选择的一部分。下一节将继续讨论：当一个标识进入 URL、日志和客户端数据后，能够被引用与有权访问之间，为什么仍然是两件事。
