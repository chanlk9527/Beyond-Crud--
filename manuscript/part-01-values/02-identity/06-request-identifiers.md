# 一次请求里不止一个 ID

[← 迁移、合并与重建](05-migration-merge-rebuild.md) · [返回第 2 章](../02-identity.md)

用户点击“支付”后，页面等待了几秒，显示“请求失败”。他再次点击，第二次请求返回“订单已支付”。支付平台的扣款记录只有一笔，订单服务却有两次请求日志。这里没有哪个编号天然能解释全部过程：订单、两次调用、用户想完成的一次支付意图，以及支付平台的交易，属于不同的对象。

前面几节讨论的 ID 主要描述实体如何被识别、搬迁和引用。本节把时间范围缩短到一次正在发生的操作，回答另一个问题：**同一行日志里的几个 ID，分别在识别什么？**

## 2.6 一次请求里不止一个 ID

### 2.6.1 先把“支付一次”拆成几件事

可以把上面的过程写成一组标识：

```text
order_id      = order-A
request_id    = req-81       第一次 HTTP 调用
idempotency_key = pay-9f2    用户这次支付意图
trace_id      = trace-44     一条跨服务调用链
payment_id    = txn-778      支付平台创建的交易
```

它们回答的问题不同：

| 标识 | 识别什么 | 通常由谁生成 | 主要生命周期 |
| --- | --- | --- | --- |
| `order_id` | 要支付的订单实体 | 订单系统 | 订单及其历史引用有效期间 |
| `request_id` | 一次具体的请求尝试 | 接收请求的客户端或服务 | 这次调用及其日志保留期间 |
| `idempotency_key` | 希望支付一次的业务意图 | 发起业务操作的一方 | 该意图可能重试、恢复和查询期间 |
| `trace_id` | 一组相关的内部调用 | 网关或链路系统 | 一条调用链的诊断期间 |
| `payment_id` | 支付平台登记的交易 | 支付平台 | 支付记录和对账期间 |

这些值可以同时出现在一条日志里，却不应互相替代。`order_id` 相同，只说明两次调用针对同一订单；`request_id` 不同，说明服务看到了两次请求尝试；`idempotency_key` 相同，说明它们可能是在重试同一次支付意图；`payment_id` 是否相同，则取决于支付平台如何处理和返回交易。

### 2.6.2 请求 ID 识别一次尝试

请求 ID 的作用是让系统和日志区分每一次调用。第一次请求超时后，客户端重试，服务端可能看到：

```text
request_id = req-81，order_id = order-A，结果：处理超时
request_id = req-82，order_id = order-A，结果：返回已支付
```

两个 `request_id` 不应因为业务目标相同而复用。复用会让日志看起来像同一次调用，也会让网关、服务和客户端难以判断哪一次响应已经返回。请求 ID 通常在请求进入某个边界时生成或传入，并随错误、访问日志和响应元数据一起记录。

它也不能承担“禁止重复扣款”的责任。请求 ID 只识别调用，不自动约束调用产生的业务效果；如果服务在第一次请求已经扣款、第二次请求又创建一笔支付，两个请求 ID 都完全合法，结果仍然错误。

### 2.6.3 幂等键识别一次业务意图

幂等键表达的是另一件事：“对于这个订单，这次支付意图只应产生一个业务结果。”客户端可以在首次尝试和重试时继续携带同一个键：

```text
第一次：order_id = order-A，idempotency_key = pay-9f2
重试：  order_id = order-A，idempotency_key = pay-9f2
```

服务端需要规定这个键的作用域和保存时间。例如，`pay-9f2` 可以只在某个商户和支付操作范围内唯一，并关联订单、金额、币种等请求参数。重试时参数一致，系统可以返回第一次已保存的结果；如果同一个键被用于另一笔订单或不同金额，系统应拒绝，而不是把两个意图悄悄合并。

幂等键不是请求 ID，也不是永久的订单身份。它可能在支付结果确认、超时查询和重试窗口结束后过期；订单则继续存在。过期后是否允许复用，要看系统是否仍可能收到迟到的请求或补偿消息。若旧请求仍可能到达，过早复用会让迟到请求撞上新意图。

幂等记录还要保存足够的信息解释结果来自哪里：业务作用域、键、请求参数摘要、处理状态、最终结果和过期时间。只保存“键已经用过”而不保存结果，无法在重试时稳定回答调用方；只保存键而不校验参数，则可能把不同支付金额误认为同一次意图。

### 2.6.4 链路 ID 把内部调用串起来

一次支付请求可能经过网关、订单服务、库存服务和支付适配器。`trace_id` 让这些服务的日志能够被归为同一条调用链：

```text
trace-44
 ├─ 网关：收到请求
 ├─ 订单服务：校验 order-A
 ├─ 支付适配器：调用外部平台
 └─ 订单服务：等待响应超时
```

链路 ID 适合回答“这次内部调用经过了哪些服务”，不适合回答“用户针对哪个订单发起了哪种业务意图”。一条链路可能包含多个订单或多个内部重试；一个业务操作也可能因为异步回调、队列重新投递而跨越多条链路。需要把它和 `order_id`、`request_id`、幂等键一起记录，才能从诊断路径回到业务对象。

服务之间转发请求时，可以沿用原来的链路 ID，也可以为新的异步阶段建立新的链路并保存父子关系。无论采用哪种方式，都要有统一约定，否则同一个字段在不同服务里一会儿表示 HTTP 请求，一会儿表示整条业务流程，最后只能靠猜。

### 2.6.5 外部交易号连接另一套系统

支付平台通常会返回自己的交易号，例如 `payment_id = txn-778`。这个值由支付平台定义，订单服务不能把自己的 `request_id` 当作支付平台交易号，也不能假定订单号会自动出现在支付平台的对账文件中。

系统应保存跨系统关联：

```text
order_id          = order-A
idempotency_key   = pay-9f2
payment_id        = txn-778
provider_request  = provider-501
```

`payment_id` 用于查询支付状态、接收回调和核对账单；`provider_request` 如果平台提供，则可以帮助定位某一次向平台发出的调用。不同平台的字段命名和生命周期可能不同，接入层应明确哪一个是交易实体、哪一个只是请求尝试。

外部回调可能晚于原始请求，也可能只携带平台交易号。服务收到回调后，应通过保存的映射找到订单和幂等记录，并验证回调属于哪个商户、金额和币种是否匹配。不能因为回调中的订单号看起来正确，就跳过来源验证；也不能因为原始请求超时，就把“没有收到响应”当作“支付没有发生”。

### 2.6.6 响应丢失时，怎样留下可解释的证据？

回到开篇，第一次请求可能经历了这样的顺序：订单服务接受 `req-81`，用 `pay-9f2` 调用支付平台，平台创建 `txn-778`，随后网络中断，客户端没有收到结果。客户端重新发起 `req-82`，仍携带 `pay-9f2`。服务查到幂等记录或向支付平台查询后，返回同一支付结果，而不是盲目创建新交易。

一次可排查的日志至少要能把这些记录连起来：

```text
request_id=req-81  trace_id=trace-44  order_id=order-A
idempotency_key=pay-9f2  payment_id=txn-778  event=provider-created

request_id=req-82  trace_id=trace-91  order_id=order-A
idempotency_key=pay-9f2  payment_id=txn-778  event=replay-result
```

两次请求的 `trace_id` 可以不同，因为它们是两条调用链；`idempotency_key` 和 `payment_id` 相同，因为它们指向同一次业务意图及同一笔外部交易。这样的记录既能解释客户端为何重试，也能支持订单、支付和平台账单之间的对账。

日志不应把秘密凭证当作普通 ID 记录。幂等键如果只是关联线索，可以按业务需要记录；如果某个系统把它设计成可直接获得操作权限的秘密值，就应按凭证处理并限制暴露。支付平台的访问令牌、签名材料和完整卡信息则不属于关联标识，不能为了“方便排查”写入普通日志。

### 2.6.7 用一张关系表检查职责是否混淆

设计一次跨服务操作时，可以逐项检查：

| 检查问题 | 应该由哪个标识回答 |
| --- | --- |
| 这次操作针对哪条订单？ | `order_id` |
| 服务实际收到了哪一次调用？ | `request_id` |
| 两次调用是否表达同一次支付意图？ | `idempotency_key` |
| 这次调用经过了哪些内部服务？ | `trace_id` |
| 支付平台登记的是哪笔交易？ | `payment_id` |
| 旧请求和新请求怎样回到同一业务结果？ | 幂等记录与这些标识的映射 |

如果一个字段必须同时回答两三行的问题，通常说明职责没有分开。可以共用一个值，但要明确这是有意的约束，并接受它带来的生命周期、暴露范围和冲突处理要求。

本节的结论是：**请求 ID 识别调用尝试，幂等键识别可重试的业务意图，实体 ID 识别业务对象，链路 ID 组织内部证据，外部交易号连接另一套系统。** 下一节将把这些标识放进一套完整的订单设计，检查生成、引用、迁移、重试和对账能否同时成立。
