# 唯一性与稳定性：身份在哪些变化中保持成立？

[← 这个 ID 在识别什么？](01-identity.md) · [返回第 2 章](../02-identity.md)

上一节把几种标识分开了：实体身份说明“是不是同一个对象”，主键说明“怎样在表里找到一行”，公开标识说明“别人怎样引用它”，请求标识说明“这是哪一次调用”。现在还要给实体身份补上两个条件：**唯一要在哪个范围内成立，稳定要持续到什么时候？**

## 2.2 唯一，不是没有范围的形容词

### 2.2.1 两个 `id = 1` 什么时候冲突？

手机和电脑各自有一条 `id = 1` 的待办。在各自的本地表里，它们都没有冲突；只有当两张表进入同一个同步空间，而系统仍把这个数字当作共同身份时，问题才出现：两条不同的待办被当成了同一条。

```text
手机数据库       id = 1
电脑数据库       id = 1
        ↓ 合并到同一同步空间
共享待办集合     需要能够区分两条实体
```

所以，“`id` 唯一”必须补上范围：是一张表、一个数据库、一个租户、整个服务、所有区域，还是某个时间窗口？没有这个限定，唯一性就没有可验证的含义。

边界应当跟着使用场景走。单表查询只需要表内唯一；租户内的订单号可以在不同租户之间重复；跨区域同步的实体 ID 则必须覆盖所有参与同步的副本。让本地行号承担全局身份，会增加不必要的协调；让跨服务关联只使用局部编号，则会在系统合并时暴露冲突。

可以先写下标识真正经过的范围：

| 使用场景 | 至少需要在哪个范围内不冲突 | 常见误判 |
| --- | --- | --- |
| 查询一条本地记录 | 单表或单库 | 把表内唯一当成系统全局唯一 |
| 租户内展示订单号 | 单租户 | 以为必须消耗全局编号 |
| 多设备同步实体 | 所有参与同步的设备和副本 | 继续使用各设备的本地自增值 |
| 跨服务关联记录 | 参与关联的系统和区域 | 只在发送方数据库中唯一 |

有些标识只需在一段时间内不重复。验证码、上传会话号和临时导入批次号，可能只在有效期内承担区分作用。设计时仍要说清三件事：从什么时候开始生效，到什么时候仍有效，过期后能否重新分配。订单号、公开链接和审计记录通常不能因为“不活跃”就复用，否则旧文档会指向新对象。

### 2.2.2 稳定，指的是搬家后仍能认出它

唯一性解决“会不会撞”，稳定性解决“搬家后是不是同一个”。数据库拆分、分片、备份恢复、导入导出和重建索引，都可能改变一行的位置、内部编号或表示方式，却不一定改变业务对象。

```text
旧库：internal_id = 17，entity_id = order-A
        ↓ 迁移
新库：internal_id = 9042，entity_id = order-A
```

这里，`internal_id` 负责当前存储中的定位，`entity_id` 负责跨存储识别业务对象。**稳定并不意味着所有字段永远不能改变，而是要明确哪些变化仍属于同一对象。** 订单换了分片，用户手里的链接、支付对账记录和审计证据仍应指向 `order-A`；订单被复制成另一笔独立交易，则应获得新身份。

重建记录也不等于重建身份。灾备恢复可能使用一套全新的数据库，导入外部系统也可能无法保留原来的自增主键。如果旧编号已经出现在链接或文档中，就要保存旧编号到新身份的映射，或者把旧编号作为别名，并规定它可以解析到什么时候。

合并数据时，两个来源都声称自己有 `customer_id = 7`，不能简单挑一个编号留下。先要判断它们是否代表同一个客户：不是同一个，就生成不同的新身份；确实是同一个，就保留来源和合并依据，日后才能解释历史记录为何指向同一对象。

### 2.2.3 把保证写成可以检查的表

选择生成算法之前，可以先为每个标识写下三项承诺：识别谁，在哪个范围内唯一，要稳定到什么时候。

| 标识 | 识别对象 | 唯一性范围 | 需要稳定到什么时候 |
| --- | --- | --- | --- |
| 本地行号 | 一条本地记录 | 单设备单表 | 记录存在期间 |
| 待办实体 ID | 一条待办 | 所有同步副本 | 待办及其历史引用有效期间 |
| 公开订单号 | 用户可引用的订单 | 产品规定的业务范围 | 外部引用和审计仍有效期间 |
| 导入批次号 | 一次导入任务 | 导入系统及有效窗口 | 排查和对账完成前 |

这张表不要求所有标识都全局唯一，也不要求所有标识都永久稳定。它的作用是把“唯一”和“稳定”从口号变成设计承诺：系统知道自己要防止哪一种冲突，也知道一次迁移或重建之后必须保留什么。

本节的结论是：**唯一性必须带着范围，稳定性必须带着生命周期。** 接下来比较自增值、随机标识和按时间排序的标识时，问题就不再是“哪个 ID 最好”，而是每种生成方式替哪一个边界提供保证，又把哪些协调成本交给了系统。
