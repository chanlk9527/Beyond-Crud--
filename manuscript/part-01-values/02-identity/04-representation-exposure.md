# 表示与暴露：能引用不等于有权限

[← 生成方式](03-generation.md) · [返回第 2 章](../02-identity.md)

用户在订单详情页复制了一个链接，发给同事核对。同事已经登录自己的账户，点开后看到了订单里的收货地址。这个功能有没有问题，取决于产品是否允许同事查看这笔订单；“链接是真的”和“同事已经登录”都不足以作出判断。

上一节讨论了怎样生成 ID。现在，ID 已经离开数据库，进入地址栏、聊天消息和别人的浏览器。生成时的唯一性仍然成立，但系统还必须回答：这个值怎样被理解，谁能看见它，拿到它之后能做什么？

## 2.4 表示与暴露：能引用不等于有权限

### 2.4.1 地址栏里的编号承担什么承诺？

假设订单详情页使用这样的地址：

```text
/orders/SH-2026-001048
```

`SH-2026-001048` 是用户可引用的订单号。客服可以照着它查找记录，用户可以把它保存在书签里。这里的“公开”指它允许出现在用户可见的位置，并不表示订单内容对所有人开放。

编号可以方便人阅读，却不宜让每个调用方都自行解释。假设 `SH` 最初表示接单区域，后来订单转到另一地区处理，客户端如果仍从前缀推导当前归属，就会得到过时的结果。需要当前区域时，应读取接口中明确提供的区域字段；编号的格式是否包含业务含义、含义是否随时间变化，应由协议规定。

**用于引用的表示一旦对外提供，就成为调用方依赖的约定。** 大小写是否等价、前导零能否省略、连字符是否只是显示分隔符，都应有统一规则。例如，产品若约定 `001048` 是完整编号，导出程序就不能擅自把它转换成数字 `1048`，再期待导入程序总能补回原值。显示时缩写长 ID 可以方便浏览，但复制链接和提交请求仍应使用完整值。

稳定引用也需要区分对象与权限。只要产品仍承诺旧链接有效，这个链接就应继续识别原来的订单；用户离开项目后，系统却可能不再允许他查看订单。链接仍然指向同一个对象，与当前访问是否获准，可以同时得到不同答案。下一节再讨论存储变化后怎样维持这种引用关系。

### 2.4.2 把顺序号换成随机值，检查还在吗？

如果订单地址是 `/orders/1048`，访问者很容易尝试 `/orders/1049`。在服务端没有检查权限的情况下，相邻编号可能直接暴露另一位用户的订单。换成难以猜测的随机标识，能够增加批量猜测有效地址的难度；但开篇的同事已经通过聊天拿到了真实链接，根本不需要猜。

**不可预测性影响别人找到标识的难度，对象级授权决定他找到后能否访问。** OWASP 的[直接对象引用防护指南](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html)也明确指出，即使使用复杂标识，仍须检查调用者对具体对象的权限。

回到订单详情页，可以把服务端的处理写成下面的伪代码。本例假设订单号在租户内唯一，且访问订单需要登录：

```text
actor = requireAuthenticatedUser(request)
tenant = requireTenantMembership(actor, request.tenantId)
order = findOrder(tenant.id, request.orderNumber)
requirePermission(actor, "view", order)
return orderDetails(order)
```

认证确定调用者是谁；租户成员检查确认他可以进入这个租户；对象级授权再判断他能否查看这笔订单。属于同一租户不一定能看全部订单，有权查看也不一定有权取消。代码中的检查是逻辑责任，不要求各自对应一次数据库查询；查询本身也可以限制在调用者有权访问的对象集合内。

客户端传来的 `tenantId` 同样只是待验证的输入。在 URL 中加上租户前缀，并不会自动建立租户隔离。把 ID 藏进请求体、隐藏表单字段，或只在界面上隐藏按钮，也不会替服务端完成这项检查。

因此，评估这里的设计时，不应只检查“随机编号是否够长”。更直接的验证是：让账户甲持有账户乙订单的完整编号，分别尝试查看、修改和导出，预期都应遵循相应的权限规则。这样才能区分系统是在保护对象，还是仅仅期待访问者不知道地址。

### 2.4.3 “知道链接就能看”需要单独设计

有些产品确实允许用户创建“任何持有链接的人都能查看”的分享链接。此时，系统有意把持有某个秘密值作为获准访问的依据。这个值承担了访问凭证的职责，不能再按普通公开编号处理。

仍以订单为例，产品可以保持订单号不变，另外创建一条只读分享记录：

```text
公开订单号：SH-2026-001048 → 识别订单
分享凭证：<不可预测的秘密值> → 授予该订单的限时只读访问
```

服务端收到分享请求后，需要验证凭证，并依据对应的分享记录确认目标订单、允许的动作、到期时间和撤销状态。撤销分享时，让这份授权失效即可；订单身份无需随之改变。持有只读链接也不应自动获得修改、取消或访问其他订单的能力。

这里增加了凭证生成、保存、验证和撤销的责任，换来的是独立管理分享权限的能力。若直接把永久订单 ID 当成分享秘密，关闭一次分享就可能要求更换订单的对外引用，原来的书签和客服记录也会受到影响。

**实体标识的生命周期和分享授权的生命周期应分别定义。** 本节只建立这个区别：普通订单接口依据登录者的权限判断访问；分享入口依据产品明确授予的分享权限判断访问。完整的授权实现放在后续章节展开。

### 2.4.4 ID 离开页面后，还会去哪里？

关闭详情页不会让编号消失。地址可能留在浏览器历史中，请求路径可能进入访问日志，客服截图可能包含订单号，导出文件和客户端缓存也可能保存它。判断一个标识暴露给谁，需要沿这些实际出口查看，不能只看页面上有没有显示。

一个随机用户 ID 即使没有编码姓名，也可以把多条行为记录关联到同一个账户；如果另一个数据集保存了该 ID 与姓名的对应关系，两者仍能连接起来。因此，“看不出含义”不足以说明数据已经匿名。需要限制的是哪些信息能够被关联，以及哪些使用者有权获得这种关联。

这些出口各有用途，也有不同的保留要求：

| 出现位置 | 使用目的 | 需要明确的处理约定 |
| --- | --- | --- |
| URL 与书签 | 再次打开同一个对象 | 保留稳定引用，每次访问重新判断当前权限 |
| 运行日志 | 排查一次操作涉及哪个对象 | 按排查需要记录标识，限制读取者与保存时间 |
| 对外错误信息 | 帮助用户反馈问题 | 可提供排查编号，避免附带无关对象或租户信息 |
| 导出文件 | 交接、分析或再次导入 | 保留完整编号及必要作用域，按内容限制接收范围 |
| 客户端缓存 | 加快访问或支持离线使用 | 按账户和租户隔离，明确退出和切换账户时的清理规则 |

日志尤其要区分普通标识与秘密凭证。订单 ID 可以成为排查线索，分享凭证原文却可能让日志阅读者获得访问能力。记录“哪条分享记录被使用”通常不要求记录那段秘密值。[OWASP 日志指南](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#data-to-exclude)建议避免直接记录访问令牌等秘密，并按用途处理敏感数据。

缓存也不能把“以前允许访问”无限延长。切换账户后，上一账户缓存的订单不应仅因为 ID 命中就展示给新账户；已经下载到离线设备上的内容，则不能指望一次服务端权限撤销立即从设备上消失。这是保存副本带来的限制，需要在离线能力与数据保留约定中说明。

回到开篇，同事拿到订单链接，只说明他知道要引用哪个对象。普通详情页仍须检查他的访问权限；若用户有意分享，就应通过有明确范围和生命周期的分享授权完成。公开表示、对象身份和访问凭证的职责分清之后，还剩一个实际问题：订单换了数据库，用户保存的链接怎样继续找到它？下一节将讨论迁移、合并与重建中的身份映射。
