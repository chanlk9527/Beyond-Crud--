# 这个 ID 在识别什么？

[第 2 章：ID 不只是数据库主键](../02-identity.md)

暂时把同步放到一边，只看手机上的待办列表。我们创建一条“买牛奶”，随后把标题改成“买两盒牛奶”，再把它标记为已完成。页面上的文字和状态都变了，但用户仍认为自己在处理原来的那条待办。应用也应当把提醒、备注和修改记录继续归在它下面。

## 2.1 这个 ID 在识别什么？

### 2.1.1 内容变化了，对象还是原来的对象

需要在变化中持续辨认的对象，通常称为**实体**。一条待办、一个账户、一张订单都可以是实体。实体的身份回答“是不是同一个对象”，标题、状态、金额等属性则描述“这个对象现在是什么样”。ID 是 identifier 的缩写，即标识符；在这里，我们用一个标识值指称某个实体。

例如，给刚才的待办分配标识 `task-A`。这个写法只是为了方便阅读，暂不讨论它怎样生成：

```text
task-A：买牛奶     → 未完成
   ↓ 修改标题
task-A：买两盒牛奶 → 未完成
   ↓ 标记完成
task-A：买两盒牛奶 → 已完成
```

三行描述同一条待办在不同时刻的状态。若每次修改标题都生成新的实体 ID，原来指向 `task-A` 的备注和提醒就需要跟着改，否则它们会留在旧对象上。对于这个应用，改标题只是修改属性，没有创建另一条待办的业务含义，因此应保留实体标识。

反过来，今天和明天都可以各有一条“买牛奶”。两条待办的标题甚至其他属性都可能相同，用户却可以只完成其中一条。**内容相同不足以判定是同一个实体，内容不同也不足以判定是不同实体。** 所以，标题适合搜索和显示，不能在本例中单独承担身份标识。

“复制”和“同步”让这个区别更清楚。用户点击“复制待办”，本例约定产生一条可以独立编辑的新待办，它应获得新身份；应用把原待办同步到电脑，则只是增加一份关于同一实体的记录，应保留识别原待办的依据。两者都可能在存储中新增一行，业务含义却不同。

删除后再创建一条同名待办，本例也把它视为新对象，旧备注不会自动转给它；如果产品提供“恢复已删除待办”，恢复的才是原对象。这个区别来自操作的业务约定，数据库无法仅凭两条记录的内容替我们作出判断。

### 2.1.2 数据库主键识别的是哪一行

把待办存入关系数据库，通常会为表声明主键。主键是一列或一组列，用于在该表中唯一标识一行。以 PostgreSQL 为例，主键约束要求这些值唯一且非空，也允许使用多列组成主键；它并不要求必须有一个名叫 `id` 的自增整数字段。具体语义见 [PostgreSQL 主键约束文档](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-PRIMARY-KEYS)。

如果应用只使用一个数据库，并且一条待办始终对应一行，那么直接用主键值作为待办的标识，可以是一个充分而简单的设计。比如 `tasks.id = 17` 既用于查找那一行，也用于指称对应的待办。区分这两种职责，不代表一定要增加两个字段。

开篇的多设备场景改变了这个前提。手机表中的 `id = 1` 和电脑表中的 `id = 1` 分别满足各自表内的唯一要求，却指向两条不同的待办。即使两张表都声明了主键，数据库也不会因此为它们建立跨设备的共同编号规则。

反过来，同一条待办同步到另一个设备时，也可能在目标表中取得不同的本地主键。为了表达这个关系，可以将本地行号与共享的待办标识分别保存：

```text
                         同一条待办 task-A
                         /             \
手机本地记录：local_id = 1               电脑本地记录：local_id = 27
              task_id = task-A                        task_id = task-A
```

图中两个 `local_id` 分别用于各自数据库中的行定位，`task_id` 用于辨认它们记录的是同一条待办。这里把字段拆开，是为了容纳已有的本地编号；如果共享标识本身能满足本地表的要求，也可以直接用它作为主键。怎样生成这个共享标识，后面再讨论。

**主键约束提供表内行的唯一性；让这个值同时承担实体身份，还需要应用定义它的使用范围和变化规则。** 主键也不是记录的物理地址：数据库怎样存放、搬移一行，不应被误认为业务对象换了身份。我们这里说的“定位”，是按键查找记录。

### 2.1.3 给人看的编号，也是在指称对象

在团队待办工具中，同事可能会说：“帮我看看 `TODO-104`。”这个编号方便搜索、沟通，也可能出现在分享链接里。它承担的是公开标识的角色：应用允许使用者通过它引用一条待办。

公开标识与内部主键可以使用同一个值，也可以分开。例如，内部使用不便口述的长标识，对外提供简短编号。分开之后，就需要维护公开编号到实体的对应关系；使用同一个值，则需要让它同时满足存储与对外引用的要求。不能只看到多一个字段的便利，也要看到多一份映射的维护责任。

一旦编号出现在聊天消息或书签里，引用就离开了数据库的直接控制范围。重建内部记录时可以调整内部编号，但已经发出去的链接仍需要找到原对象；如果决定更换公开编号，就要考虑旧编号怎样继续解析。稳定引用的具体做法将在后文展开。

这里有一个容易混淆的分类关系。**实体标识说明识别谁，主键说明在表中承担什么约束，公开标识说明交给谁使用；它们是不同角度，并非互斥的几种 ID。** 一个值可以同时承担三种角色，也可以由多个值通过映射共同指向一个实体。

### 2.1.4 对象的编号与操作的编号

给待办 `task-A` 改标题是一次操作，把它标记为完成又是另一次操作。日志如果只记录 `task-A`，可以查到关于这条待办的所有记录，却不能仅凭这个值区分是哪一次调用。

因此，我们还可以给调用分配请求标识。本例约定每次客户端发出的调用使用一个新的 `request_id`：

```text
request_id = req-81，task_id = task-A，修改标题
request_id = req-82，task_id = task-A，标记完成
```

两个请求操作同一实体，所以 `task_id` 相同；它们是两次调用，所以 `request_id` 不同。这里的命名和粒度是本例的约定，实际系统需要在接口与日志规则中明确，不能只从字段名推断。

若一次用户操作还会触发多个内部调用，可以另约定一个关联标识，把相关记录归为一组。它识别的是一段协作过程，而不是那条待办。把同组记录连起来，有助于排查发生了什么，却不自动保证业务动作只执行一次。请求重试时怎样辨认重复意图，以及幂等键承担什么职责，留到本章后面的请求案例中讨论。

对实体、调用和协作过程分别编号，并不是为了让每行日志更长。**它们各有不同的“一次”和不同的结束时间。** 待办可以存在几个月，一次调用可能很快结束；把请求编号当成待办编号，会把对象的连续存在与操作的反复发生混在一起。

### 2.1.5 用操作结果检查身份约定

回到待办应用，先不选择生成算法，也可以写出一组明确的预期。以下检查依据的是本例的产品约定，而不是某个 ID 库的行为。

表 2-1：不同操作对待办身份的影响。

| 操作 | 实体身份的预期 | 可以观察的结果 |
| --- | --- | --- |
| 改标题、标记完成 | 保持原身份 | 原备注仍属于这条待办 |
| 新建同名待办 | 产生新身份 | 完成其中一条不改变另一条 |
| 点击“复制待办” | 产生新身份 | 两条待办可以独立编辑 |
| 同步到另一台设备 | 保持原身份 | 两份记录可被认作同一条待办的副本 |
| 删除后重新创建同名待办 | 产生新身份 | 旧引用不会转而指向新建对象 |
| 恢复已删除的原待办 | 恢复原身份 | 原有引用仍指向被恢复的对象 |

这些检查并不要求同步后的数据立即一致，也没有解决并发编辑的问题。它们只确定同步和编辑应围绕哪个对象进行。如果连对象都认错了，后面的状态合并再精确，也是在合并两件不同的事。

现在，我们已经知道哪些动作保留身份、哪些动作创建新身份，也区分了实体标识、存储主键、公开编号与请求标识。还剩一个直接的问题：两个设备都给各自的新待办分配了 `1`，应当怎样让系统分清它们？回答之前，需要先说明“唯一”究竟要在哪个范围内成立。
