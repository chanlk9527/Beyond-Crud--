# 这个 ID 在识别什么？

[第 2 章：ID 不只是数据库主键](../02-identity.md)

先看一条最普通的待办。我们创建“买牛奶”，把标题改成“买两盒牛奶”，然后将它标记为已完成。它的标题和状态发生了变化，用户却始终认为自己处理的是同一条待办；提醒、备注和修改记录也应该继续归属于它。

理解这件事不需要先讨论 ID 的生成算法。更早的问题是：**系统需要持续辨认的，究竟是哪个对象？** 本节从这条待办出发，依次区分实体身份、数据库主键、公开编号和请求标识。

## 2.1 先确定：ID 要让谁保持可辨认？

### 2.1.1 改了内容，为什么还是同一条待办？

需要在变化中持续辨认的对象，通常称为**实体**。一条待办、一个账户或一张订单，都可以是实体。实体身份回答“是不是同一个对象”；标题、状态、金额等属性描述“这个对象现在是什么样”。

ID 是 identifier 的缩写，即标识符。这里先用 `task-A` 指称刚才那条待办，暂时不讨论它怎样生成：

```text
task-A：买牛奶     → 未完成
   ↓ 修改标题
task-A：买两盒牛奶 → 未完成
   ↓ 标记完成
task-A：买两盒牛奶 → 已完成
```

三行描述的是同一条待办在不同时刻的状态。如果每次改标题都生成新的实体 ID，原来指向 `task-A` 的备注和提醒就必须一并迁移；否则，它们会留在旧对象上。对这个应用来说，改标题只是修改属性，并不意味着“创建另一条待办”，所以实体标识应保持不变。

反过来，今天和明天可以各有一条“买牛奶”。两条待办的标题甚至其他属性都可能相同，用户却可以只完成其中一条。**内容相同不足以判定是同一个实体，内容不同也不足以判定是不同实体。** 标题适合搜索和显示，在本例中却不能单独承担身份标识。

“复制”“同步”和“恢复”可以进一步检验这条约定：

- 点击“复制待办”会产生一条可以独立编辑的新待办，因此应获得新身份。
- 把原待办同步到电脑只是增加一份副本，仍应保留原实体的身份。
- 删除后重新创建同名待办是新对象，旧备注不会自动转给它；恢复已删除待办时，恢复的才是原对象。

这几种操作都可能在数据库中新增一行，但业务含义并不相同。数据库无法只凭记录内容替我们作出判断，身份规则必须来自产品对这些操作的定义。

### 2.1.2 主键找到的是哪一行？

把待办存入关系数据库后，通常会为这张表声明主键。主键可以是一列，也可以由多列组成，用来在表内唯一定位一行。以 PostgreSQL 为例，主键值必须唯一且非空，但主键并不一定叫 `id`，也不一定是自增整数。具体语义见 [PostgreSQL 主键约束文档](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-PRIMARY-KEYS)。

如果应用只使用一个数据库，并且一条待办始终对应一行，那么直接把主键值作为待办标识，可能就是充分而简单的设计。例如，`tasks.id = 17` 既能定位这一行，也可以指代对应的待办。区分“主键”和“实体身份”并不意味着一定要增加两个字段；在前提成立时，一个值可以同时承担两种职责。

一旦数据需要同步到多台设备，前提就变了。手机表中的 `id = 1` 和电脑表中的 `id = 1` 都满足各自表内的唯一约束，却可能指向两条不同的待办。两张表都声明主键，并不会让数据库自动为它们建立跨设备的共同编号规则。

反过来，同一条待办同步到另一台设备时，也可能在目标表中得到不同的本地主键。因此，可以把本地行号和共享的待办标识分开保存：

```text
                         同一条待办 task-A
                         /             \
手机本地记录：local_id = 1               电脑本地记录：local_id = 27
              task_id = task-A                        task_id = task-A
```

两个 `local_id` 只负责在各自的数据库中定位行，`task_id` 才说明这两行记录的是同一条待办。把两个字段分开，是为了容纳已经存在的本地编号；如果共享标识本身也能满足本地表的约束，也可以直接用它作为主键。共享标识如何生成，后面再讨论。

**主键约束提供的是表内行的唯一性；让这个值同时承担实体身份，还需要应用定义它的使用范围和变化规则。** 主键也不是记录的物理地址。数据库搬移或重排一行，不应被误认为业务对象换了身份；这里说的“定位”，只是按键查找记录。

### 2.1.3 对外引用的标识，和内部主键是什么关系？

假设数据库里有这样一条待办：

```text
内部主键：id = 873421
公开编号：TODO-104
标题：给房东发消息
```

数据库可以用 `873421` 找到这一行；用户、客服或分享链接则可以使用更容易阅读的 `TODO-104`。这两个值都指向同一条待办，但服务的对象不同：主键主要服务于存储系统，公开编号主要服务于系统外部的引用者。

公开编号和内部主键可以是同一个值，也可以分开：

- 如果应用规模小、内部编号也适合出现在界面和链接中，可以直接共用一个值。
- 如果内部主键很长、可读性差，或者未来可能更换存储方式，可以另外设置公开编号。

分开之后，系统必须保存“`TODO-104` 对应哪一个实体”的关系。共用一个值则少维护一层映射，但这个值必须同时满足数据库和对外引用的要求。两种设计都可以成立，关键是明确谁会使用这个值，以及它需要保持多久。

一旦公开编号出现在聊天消息、书签或外部系统中，它就不再只是数据库里的临时字段。即使内部记录后来迁移到另一张表，`TODO-104` 仍然应该能够找到原来的待办；如果确实要更换编号，还要决定旧编号是否继续解析。稳定引用的具体做法将在后文展开。

这里要区分三个角度：**实体身份说明要识别谁，主键说明怎样在表中找到一行，公开标识说明别人怎样引用它。** 它们可以由同一个值承担，也可以由不同值通过映射共同完成。

### 2.1.4 待办的编号，为什么不能代替请求编号？

同一条待办可以被操作很多次。比如，用户先修改标题，之后又把它标记为完成：

```text
request_id = req-81，task_id = task-A，修改标题
request_id = req-82，task_id = task-A，标记完成
```

两条记录里的 `task_id` 相同，因为它们操作的是同一条待办；`request_id` 不同，因为它们是两次独立的调用。这里的两个编号回答不同的问题：

- `task_id`：这次操作针对哪个业务对象？
- `request_id`：这是哪一次调用？

如果日志只记录 `task_id`，我们仍然可以找到这条待办的全部历史，却无法仅凭这个值区分“改标题”和“标记完成”，也无法判断某条错误日志对应哪一次调用。反过来，如果只记录 `request_id`，我们知道发生过一次调用，却不知道它操作的是哪条待办。

本例约定客户端每发起一次调用，就使用一个新的 `request_id`。实际系统还需要明确请求标识的粒度：它可以识别一次网络请求、一次服务内部调用，或一次更大的操作尝试。不能只根据字段名推断它的含义。

一次用户操作还可能触发多个内部调用。此时还可以使用一个关联标识，把相关记录归为一组。不过，本节先只关注请求标识和实体标识的区别：关联标识如何组织一段调用链，以及幂等键如何处理重复意图，留到本章后面的请求案例中讨论。

为实体和调用分别编号，不是为了让每行日志更长。**它们各自对应不同的“一次”，也有不同的结束时间。** 待办可以存在几个月，一次调用可能在几毫秒内结束；把请求编号当成待办编号，就会把对象的持续存在和操作的反复发生混为一谈。

### 2.1.5 让业务动作检验身份

回到待办应用，即使还没有选择生成算法，也可以先写出明确的预期。下面的检查依据产品约定，而不是某个 ID 库的行为。

表 2-1：不同操作对待办身份的影响。

| 操作 | 实体身份的预期 | 可以观察的结果 |
| --- | --- | --- |
| 改标题、标记完成 | 保持原身份 | 原备注仍属于这条待办 |
| 新建同名待办 | 产生新身份 | 完成其中一条不改变另一条 |
| 点击“复制待办” | 产生新身份 | 两条待办可以独立编辑 |
| 同步到另一台设备 | 保持原身份 | 两份记录可被认作同一条待办的副本 |
| 删除后重新创建同名待办 | 产生新身份 | 旧引用不会转而指向新建对象 |
| 恢复已删除的原待办 | 恢复原身份 | 原有引用仍指向被恢复的对象 |

这些检查不要求同步后的数据立即一致，也不处理并发编辑。它们只确定同步和编辑应该围绕哪个对象展开。如果连对象都认错了，后面的状态合并再精确，也只是在合并两件不同的事。

这一节可以归结为四句话：实体身份回答“是不是同一个对象”；主键回答“怎样在一张表中找到一行”；公开标识回答“别人怎样引用它”；请求标识回答“这是哪一次调用”。接下来还要回答一个直接的问题：两个设备都给各自的新待办分配了 `1`，系统怎样避免它们发生冲突？这就需要说明，“唯一”究竟要在哪个范围内成立。
