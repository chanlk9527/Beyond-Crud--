# 第 4 章：字符串、编码与“长度”

*字符串看起来像一串文字，系统却必须决定怎样保存、比较、排序和限制它。*

开发一个功能时，字符串经常只是数据结构中的一列：用户名、文件名、标题、搜索关键词或错误消息。它们都可以放进一个 `String`，也都可以通过接口传递和写入数据库。于是我们很容易把字符串当成字符数组，认为长度就是字符数，相等就是逐个字符比较。

用户注册功能很快会暴露这个假设。下面两个用户名看起来一样：

```text
café
café
```

其中一个使用预组合字符 `é`，另一个使用 `e` 和组合重音符。界面可能把它们显示成相同的文字，程序却可能把它们当成两个不同的字符串。类似的问题也会出现在长度限制上：前端按用户看到的字符计数，数据库按字节限制，接口中间层又可能按 Unicode 码点计数。同一个输入就可能在不同边界得到不同结果。

这不是某个 API 的小陷阱。字符串至少有三种需要分别说明的性质：它在内存或网络中怎样编码，它由什么单位组成，以及业务把什么视为相同。显示内容需要保留原始形式时，唯一性比较可能需要另一份规范化的比较键；文件名需要保留用户输入时，存储路径仍然不能直接信任它。

因此，选择字符串类型和调用字符串函数以前，我们需要先说明这个值将回答什么问题：是为了显示，还是为了识别？是限制传输大小，还是限制用户感知的字符数量？是按语言规则排序，还是只判断是否完全相等？**字符串的表示、比较规则和业务用途，需要在设计中彼此对应。**

## 本章验证重点

组合字符、emoji、截断、编码往返与唯一性校验在各层使用同一套明确规则；规范化或清洗不能在没有业务约定时悄悄改写用户原始内容。
